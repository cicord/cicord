# Writing CODI plugins

A CODI plugin is a small TypeScript (or JavaScript) module that runs inside the runtime and
reacts to Discord: gateway events, slash commands, buttons and select menus, modals,
schedules, background tasks, events from other plugins and HTTP routes of the community
portal. Plugins have no Node.js APIs: every side effect goes through the `ctx` object, and
each call is checked against the capabilities that `bot.yaml` grants.

Normative references:

- [`spec/sdk/codi-sdk.d.ts`](../spec/sdk/codi-sdk.d.ts) is the `@codi/sdk` API. The
  published `@codi/sdk` package ships the same types.
- [`spec/README.md`](../spec/README.md) §4 covers plugin instances, §6 the manifest and
  capabilities, and §8 the SDK semantics.
- [`spec/schemas/plugin.schema.json`](../spec/schemas/plugin.schema.json) is the
  `plugin.yaml` schema.
- [`examples/basic/plugins/`](../examples/basic/plugins/) holds two complete plugins:
  `welcome` and `onboarding`.
- [`examples/showcase/`](../examples/showcase/) is a complete repository with four
  production-grade plugins that together use the whole SDK: `tickets` (buttons, modals,
  plugin-owned private channels), `polls` (selects, buttons with data ids, live updates,
  tasks, cross-plugin events), `levels` (message content, reactions, role rewards, cron,
  public portal route) and `moderation` (permissions, DMs, timeouts/kicks/bans, expiring KV,
  `http.fetch`). [`docs/plugin-coverage.md`](plugin-coverage.md) maps every SDK feature to
  the plugin and the end-to-end test that exercise it.

## 1. Create a plugin

```sh
codi plugin new plugins/hello        # scaffold (use --force to overwrite)
codi plugin sdk-types plugins/hello  # (re)write .codi/codi-sdk.d.ts for editors and tsc
```

`codi plugin new` writes:

```
plugins/hello/
├── plugin.yaml            # manifest (static, reviewed in PRs)
├── config.schema.json     # JSON Schema of the instance config
├── tsconfig.json          # maps "@codi/sdk" to .codi/codi-sdk.d.ts
├── .codi/codi-sdk.d.ts    # the SDK types
└── src/
    ├── index.ts           # export default definePlugin({...})
    └── codi-env.d.ts      # typed ctx.config (generated by `codi plugin typegen`)
```

The other plugin commands:

| Command | Purpose |
|---|---|
| `codi plugin build <dir>` | Bundle the plugin the way the runtime does and check the definition against the manifest. |
| `codi plugin typegen <dir>` | Generate `src/codi-env.d.ts` (the typed `PluginConfig`) from `config.schema.json`. |
| `codi plugin test <dir>` | Run the plugin on the Discord simulator with the real runtime: build, start, then a smoke test (a member joins, every command without required options is invoked). `--config` passes a config. Unit tests are separate (§8). |

Then enable the plugin on a bot in `bots/<bot>/bot.yaml`:

```yaml
spec:
  servers: [ma-commu]
  plugins:
    - name: welcome                 # instance key, unique within the bot
      source: ../../plugins/welcome # local path relative to bot.yaml (or <registry>/<plugin> + version)
      grants: [discord.messages.send, discord.channels.read, discord.members.read,
               discord.roles.assign, discord.dm.send, portal.links, storage.kv]
      config:
        channel: general
        autoRole: member
      overrides:
        ma-commu:
          config:                   # JSON merge patch (RFC 7386) over config
            message: "Salut {member}, bienvenue sur {server} !"
```

One **instance** runs per (bot, plugin instance, server). The same plugin can run twice under
two instance names with different configs, and `servers:` limits an instance to some of the
bot's servers. `codi dev --sim` hot-reloads the plugin on every save. Use the admin UI's
**Simulator** panel to trigger events and commands without Discord.

## 2. Build model

The runtime bundles plugins itself with esbuild (Go library, no Node.js involved):

- The entry is `spec.entry`, which must `export default definePlugin({...})`.
- Every imported module is bundled in. Pure-JS npm libraries work; **Node.js built-ins**
  (`fs`, `path`, `node:*`, …) are refused at build time.
- `@codi/sdk` is the only module resolved at run time (the host provides it).
- Target: ES2022, with async generators lowered. An inline source map is appended, so stack
  traces point at `src/index.ts:12:5`.
- At load time, the runtime checks the definition against the manifest:
  - a handler without its intent fails (§4);
  - `schedules`/`tasks` without `scheduler` fails;
  - `routes` without `portal.routes` fails;
  - `subscriptions` without `events.subscribe` fails.

  An unknown key in `definePlugin()`, an invalid command or an invalid cron expression is
  also a load error. The revision is then rejected, and the previous one keeps running.

## 3. Manifest (`plugin.yaml`)

```yaml
# yaml-language-server: $schema=../../../../spec/schemas/plugin.schema.json
apiVersion: codi.dev/v1alpha1
kind: Plugin
metadata:
  name: welcome                    # key: lowercase, digits, '-'
  version: 0.1.0                   # semver
  displayName: Welcome             # ≤ 64 chars
  description: Greets new members… # ≤ 280 chars
  license: Apache-2.0              # also: authors, homepage, keywords (≤ 10)
spec:
  engine: ">=0.1.0"                # runtime versions this plugin supports
  entry: ./src/index.ts
  capabilities: [discord.messages.send, discord.channels.read, discord.members.read,
                 discord.roles.assign, discord.dm.send, portal.links, storage.kv]
  intents: [ServerMembers]
  config:
    schema: ./config.schema.json
  # network:                       # required when http.fetch is requested
  #   allow: [api.example.com, "*.example.org"]
```

The manifest is static and reviewable. Commands, handlers and routes come from the code.

### Capabilities and grants

Every capability in `spec.capabilities` must also be listed in the instance's `grants` in
`bot.yaml`. Otherwise `codi validate` fails ("requests capabilities that are not granted"),
so a plugin update that asks for a new capability shows up in review. A call that is not
granted throws `CapabilityError` (its `capability` field names the missing one).

| Capability | Allows |
|---|---|
| `discord.messages.read` | `channel.messages()` (history) |
| `discord.messages.send` | `channel.send()`, `message.reply()` |
| `discord.messages.manage` | Edit/delete other authors' messages |
| `discord.reactions.manage` | `message.react()` |
| `discord.members.read` | `ctx.server.member()` |
| `discord.members.manage` | `member.setNickname()` |
| `discord.members.moderate` | `member.timeout()`, `kick()`, `ban()` |
| `discord.roles.assign` | `member.addRole()`, `removeRole()` |
| `discord.channels.read` | `ctx.server.channel()` |
| `discord.channels.manage` | `ctx.server.createChannel()` / `deleteChannel()` (plugin-owned channels) |
| `discord.threads.manage` | `channel.createThread()` |
| `discord.dm.send` | `member.send()` |
| `storage.kv` | `ctx.kv` |
| `scheduler` | `schedules`, `tasks`, `ctx.schedule` |
| `http.fetch` | `ctx.http.fetch()` to `spec.network.allow` hosts |
| `portal.routes` | `routes` |
| `portal.links` | `ctx.portal.link()` |
| `events.publish` / `events.subscribe` | `ctx.events.publish()` / `subscriptions` |

Answering the plugin's own interactions (`reply`, `defer`, `followUp`, `update`,
`showModal`) needs no capability.

**Isolation.** Each instance only reaches its own server. Channel IDs are checked to belong
to the instance's server, or to a DM channel the instance opened or received. Storage, tasks
and events are scoped to the instance or to its (bot, server).

**Network egress** (`http.fetch`). `spec.network.allow` takes public DNS hostnames with an
optional port. `*.example.com` matches subdomains, not `example.com` itself. IP literals,
`localhost` and reserved suffixes are rejected. On every request the runtime also:

- checks that every resolved address is public, and connects to the address it checked;
- re-checks every redirect hop (at most 5);
- allows only `https`.

`codi dev` relaxes these checks: plain `http` and private addresses are allowed, so a
plugin can call a local service. See spec/README.md §6.

### Intents

Event handlers need gateway intents, which the manifest must declare:

| Handler | Intent |
|---|---|
| `memberJoin`, `memberLeave`, `memberUpdate` | `ServerMembers` (privileged) |
| `messageCreate`, `messageUpdate`, `messageDelete` | `ServerMessages` (add `MessageContent`, privileged, to read `message.content`) |

**Message content is gated per plugin.** A bot connects with the union of its plugins'
intents, but a plugin that does not declare `MessageContent` still gets an empty
`message.content` (and no `attachments`), in events and in `channel.messages()`, unless
the message is the bot's own, mentions the bot or is a DM. Declare `MessageContent` only
when the plugin reads what people write (e.g. `levels` ignores very short messages); a
plugin that only needs who posted and when (flood protection, ticket activity) does not.
| `reactionAdd`, `reactionRemove` | `ServerMessageReactions` |

A bot connects with the union of its plugins' intents, plus `spec.intents` and what the
reconciler needs. Privileged intents must also be enabled in the Discord developer portal.

## 4. Configuration

`config.schema.json` is JSON Schema 2020-12. The runtime checks each instance's config
against it, per server, after merging `overrides.<server>.config` into the base config.
Schema `default`s are applied before the plugin sees `ctx.config`: at the top level, in
nested objects, in every object element of arrays (e.g. `steps[].multiple`) and through
local `$ref`s. An absent optional object is created only when its defaults cover all its
`required` fields (so an optional `webhook: {url, format}` with a required `url` stays
absent). Defaults inside `additionalProperties` maps and `oneOf`/`anyOf` alternatives are
not applied. CODI adds three keywords:

| Keyword | Values | Effect |
|---|---|---|
| `x-codi-ref` | `channel`, `category`, `role` | The value is a resource key of the server (a string, or an array of strings). The admin UI renders a picker. `codi validate` checks that the key exists on every server. |
| `x-codi-widget` | `textarea`, `markdown`, `color`, `duration` | Rendering hint for the admin UI form. |
| `x-codi-access` | `admin` (default), `moderator` | Who may edit the top-level field in the admin UI. Edits are written back to `bot.yaml` as a commit or a PR. |

From [`welcome/config.schema.json`](../examples/basic/plugins/welcome/config.schema.json):

```json
{
  "type": "object",
  "required": ["channel"],
  "properties": {
    "channel": { "type": "string", "x-codi-ref": "channel" },
    "message": {
      "type": "string",
      "default": "Welcome {member} to {server}!",
      "x-codi-widget": "textarea",
      "x-codi-access": "moderator"
    },
    "autoRole": { "type": "string", "x-codi-ref": "role" },
    "dmOnboarding": { "type": "boolean", "default": true }
  },
  "additionalProperties": false
}
```

`codi plugin typegen` turns the schema into a module augmentation, so `ctx.config` is
typed. A field that is required, or has a default the runtime applies (rules above), is
non-optional:

```ts
// src/codi-env.d.ts — generated, do not edit
declare module "@codi/sdk" {
  interface PluginConfig {
    channel: string;
    message: string;
    autoRole?: string;
    dmOnboarding: boolean;
  }
}
export {};
```

Array items follow the same rule: with `"multiple": {"type": "boolean", "default": false}`
in `steps.items`, `ctx.config.steps[0].multiple` is a `boolean`, never `undefined`. Run
`codi plugin typegen --check` in CI to catch a stale file.

## 5. The plugin definition

```ts
import { command, definePlugin } from "@codi/sdk";

export default definePlugin({
  onStart(ctx) {},          // instance start (new revision, restart)
  onStop(ctx) {},           // before stop; bounded (3 s)
  events: {},               // gateway events
  commands: {},             // slash commands
  components: {},           // buttons / select menus
  modals: {},               // modal submissions
  schedules: {},            // cron jobs
  tasks: {},                // one-shot delayed jobs
  subscriptions: {},        // events from other plugins
  routes: {},               // community portal HTTP routes
});
```

Every handler receives `ctx`:

- `ctx.plugin` (`name`, `version`, `instance`), `ctx.bot` (`key`, `user`), `ctx.server`;
- `ctx.config` (effective config);
- `ctx.log`;
- `ctx.kv`, `ctx.schedule`, `ctx.http`, `ctx.events`, `ctx.portal`.

Server resources are referenced by their **key** in `servers/<server>.yaml`
(`ctx.server.channel("general")`, `member.addRole("member")`), or by `{ id }` for resources
CODI does not manage.

### Events

From [`welcome`](../examples/basic/plugins/welcome/src/index.ts) (intent `ServerMembers`):

```ts
events: {
  async memberJoin(ctx, member) {
    const { channel, message, autoRole, dmOnboarding } = ctx.config;
    await ctx.server.channel(channel).send(render(message, { member: member.mention, server: ctx.server.name }));
    if (autoRole && !member.hasRole(autoRole)) await member.addRole(autoRole, "welcome: default role");
    if (dmOnboarding) {
      const url = await ctx.portal.link("/onboarding", { member });
      await member.send({ content: "Pick your roles:", components: [{ type: "row", components: [{ type: "link", label: "Start", url }] }] });
    }
    const total = await ctx.kv.increment("stats:joined");
    ctx.log.info("member welcomed", { member: member.id, total });
  },
},
```

The handlers are `memberJoin(member)`, `memberLeave(user)`, `memberUpdate(member, previous)`,
`messageCreate(message)`, `messageUpdate(message)`, `messageDelete({ id, channel })`,
`reactionAdd({ message, user, emoji })` and `reactionRemove(...)`. The `message` of a
reaction is partial. Events are delivered in order for each instance.

### Commands

Commands are keyed by name (lowercase letters, digits, `-` and `_`, 1–32 characters) and
synced to each server. The `command()` helper infers the type of `interaction.options`.
From `welcome`:

```ts
commands: {
  "welcome-preview": command({
    description: "Preview the welcome message", // 1–100 characters
    ephemeral: true,                             // ephemeral replies and auto-defer
    permissions: ["ManageServer"],               // default member permissions
    options: {
      member: { type: "user", description: "Member to greet (defaults to you)" },
    },
    async run(ctx, interaction) {
      const target = interaction.options.member ?? interaction.user; // User | undefined
      await interaction.reply({ content: render(ctx.config.message, { member: target.mention, server: ctx.server.name }), ephemeral: true });
    },
  }),
},
```

The rules for options:

- `type` is one of `string`, `integer`, `number`, `boolean`, `user`, `channel`, `role`,
  `mentionable` or `attachment`.
- `required` options come first in Discord.
- `min`/`max` only apply to `integer`/`number`.
- `choices` (≤ 25) only apply to `string`/`integer`/`number`.
- A command takes at most 25 options.

### Interactions: reply, defer, follow up

Discord expects an answer within 3 s. If a handler has not answered after **2 s**, the
runtime defers the interaction automatically:

- the deferral is ephemeral when the command says `ephemeral: true`;
- components get a silent "deferred update".

A later `reply()` then edits the deferred response. The first response fixes ephemerality.
After `reply()`, use `followUp()`. If a handler throws before answering, the user gets an
ephemeral *"Something went wrong while handling this interaction."*, and the error is logged.

| State | `reply()` | `defer()` | `update()` (components) | `followUp()` | `showModal()` |
|---|---|---|---|---|---|
| unanswered | initial reply | defers | edits the component's message | error | opens the modal |
| deferred (command/modal) | edits the deferred reply | no-op | error | follow-up | error |
| deferred (component) | follow-up | no-op | edits the message | follow-up | error |
| updated | follow-up | error | edits the message | follow-up | error |
| replied | error (use `followUp`) | error | error | follow-up | error |

### Components and modals

Component and modal `id`s are local to the plugin instance. On the wire the runtime
namespaces them as `c:<instance>:<id>`, which must fit Discord's 100-byte `custom_id`
limit. Handler keys are at most 80 bytes. An id may **carry data after a colon**: the lookup
falls back to the part before the first `:`, so `"vote:42"` is routed to `components.vote`,
and `componentId` stays `"vote:42"`. A sketch (`examples/showcase/plugins/polls` and
`tickets` are complete examples):

```ts
commands: {
  poll: command({
    description: "Start a poll",
    async run(ctx, interaction) {
      await interaction.reply({
        content: "Ready?",
        components: [{ type: "row", components: [
          { type: "button", id: "vote:yes", label: "Yes", style: "success" },
          { type: "button", id: "feedback", label: "Feedback…" },
        ] }],
      });
    },
  }),
},
components: {
  async vote(ctx, interaction) {           // receives "vote:yes"
    const [, answer] = interaction.componentId.split(":");
    await ctx.kv.increment(`poll:${answer}`);
    await interaction.update({ content: `Thanks, ${interaction.user.displayName}!`, components: [] });
  },
  async feedback(ctx, interaction) {
    await interaction.showModal({
      id: "feedback", title: "Feedback",
      fields: [{ id: "text", label: "Your feedback", style: "paragraph", required: true, maxLength: 500 }],
    });
  },
},
modals: {
  async feedback(ctx, interaction) {
    ctx.log.info("feedback", { text: interaction.fields.text ?? "" });
    await interaction.reply({ content: "Thanks!", ephemeral: true });
  },
},
```

Select menus are `{ type: "select", id, options: [{ value, label }], minValues?, maxValues? }`,
and the picked values arrive in `interaction.values`. Link buttons are
`{ type: "link", url, label }` and trigger no handler.

### Portal routes

`routes` expose JSON endpoints under
`/api/v1/portal/{server}/plugins/{bot}/{instance}/{path}` (spec/api.md §6). They need
`portal.routes`. Keys are `"<GET|POST|PUT|PATCH|DELETE> /path"`, and `:name` segments are
parameters (`request.params`).

`access` is required: `public`, `member`, `moderator` or `admin`. The runtime enforces it:
anonymous callers get `401`, and an insufficient role gets `403`. The handler receives:

- `request.viewer` (`{ user, member }`);
- `request.query` (the first value of each parameter);
- `request.body` (JSON).

A handler can return:

- any JSON value (`200`);
- an envelope `{ status, body?, headers? }`;
- nothing, which answers `204`.

A handler that returns both envelopes and plain JSON objects should declare its return type
(`async handler(ctx, request): Promise<RouteResponse>`): TypeScript otherwise infers a union
that does not match `RouteResponse`. Interfaces are not assignable to `Json` (no index
signature): cast records with `as unknown as Json`.

From [`onboarding`](../examples/basic/plugins/onboarding/src/index.ts):

```ts
routes: {
  "GET /steps": {
    access: "member",
    async handler(ctx, request) {
      const member = request.viewer?.member;
      if (!member) return { status: 403, body: { error: { code: "forbidden", message: "members only" } } };
      const record = await ctx.kv.get<CompletionRecord>(completionKey(member.id));
      return resolveSteps(ctx, member, record);
    },
  },
},
```

`ctx.portal.link(path, { member, expiresInSeconds })` (capability `portal.links`) returns a
signed portal URL. With `member`, opening it signs that member in, restricted to this server.
Links last 15 minutes by default, 24 hours at most. In the portal, `@codi/client`'s
`client.plugin(server, bot, instance)` and `@codi/react`'s `usePluginQuery` call the routes.

### Schedules and tasks

Both need `scheduler`. `schedules` run on a cron expression in **UTC**. Standard 5-field
cron and descriptors (`@hourly`, `@daily`, `@every 10m`) are accepted. `TZ=` prefixes are
refused. `tasks` are one-shot jobs started with `ctx.schedule.after()`. They are persisted,
so they survive restarts.

```ts
schedules: {
  digest: { cron: "0 9 * * 1", async run(ctx) {
    await ctx.server.channel("announcements").send("Weekly digest…");
  } },
},
tasks: {
  async remind(ctx, payload) {
    const { userId } = payload as { userId: string };
    await (await ctx.server.member(userId))?.send("Reminder!");
  },
},
// elsewhere: const { id } = await ctx.schedule.after(60 * 60_000, "remind", { userId });
//            await ctx.schedule.cancel(id);
```

A task often has to edit a message posted earlier (e.g. close a poll). The SDK has no
"get message by id": post with `channel.send()` (which returns the `Message`), store
`{ channelId, messageId }`, and in the task fetch it back with
`channel.messages({ before: <messageId + 1>, limit: 1 })` (the newest message strictly
before `id + 1` is the message itself). `examples/showcase/plugins/polls` does this.

### Plugin-owned channels

`ctx.server.createChannel({ name, type, category, topic, overwrites })`
(`discord.channels.manage`) creates a channel recorded as owned by the plugin instance: the
reconciler never touches or prunes it, even with `prune: true`, and only that instance can
`deleteChannel()` it. `overwrites` keys are `"@everyone"`, a role key, `"role:<id>"` or
`"member:<id>"`. Give the bot itself access (`member:${ctx.bot.user.id}`) when the channel
hides `@everyone`, or a bot without Administrator locks itself out. See
`examples/showcase/plugins/tickets`.

### Cross-plugin events

`ctx.events.publish(topic, payload)` (`events.publish`) delivers to the instances of the same
(bot, server). Topics are namespaced with the publisher's plugin name, so plugin `xp` calling
`publish("levelUp", …)` reaches `subscriptions["xp.levelUp"]` (`events.subscribe`).

```ts
// plugin "xp"
await ctx.events.publish("levelUp", { userId: member.id, level: 5 });
// another plugin
subscriptions: {
  async "xp.levelUp"(ctx, payload) {
    const { userId, level } = payload as { userId: string; level: number };
    ctx.log.info("level up", { userId, level });
  },
},
```

### Storage, HTTP, logging

- `ctx.kv` (`storage.kv`) is a JSON key-value store scoped to the instance, with these
  operations:
  - `get`;
  - `set(key, value, { ttlSeconds })`;
  - `delete`;
  - atomic `increment`;
  - `list({ prefix, limit, cursor })`.
- `ctx.http.fetch(url, { method, headers, body, timeoutMs })` (`http.fetch`) returns
  `{ status, headers, text(), json() }`.
- `ctx.log.debug/info/warn/error(message, fields)` and `console.*` go to the runtime log,
  tagged with the plugin instance.

### Globals

Plugins get `setTimeout`, `setInterval`, `clearTimeout`, `clearInterval`, `queueMicrotask`
and `console`. Timers belong to the handler that created them and stop with it. There is no
`process`, `fetch`, DOM or Node.js API.

## 6. Execution model and limits

Each plugin instance gets its own VM (Sobek) and one event loop. Handlers interleave at
`await` points, like in Node.

| Limit | Value |
|---|---|
| Synchronous JS per event-loop turn | 50 ms (a runaway turn aborts the handler; the instance keeps running) |
| Module evaluation at start | 2 s |
| Handler duration, awaits included | 10 s (async work it started is cut too) |
| Auto-defer of interactions | 2 s |
| `onStop` | 3 s |
| `http.fetch` | 10 s default timeout (`timeoutMs` up to the handler timeout), response ≤ 5 MiB, request body ≤ 1 MiB, ≤ 5 redirects |
| KV | key 1–512 bytes, value ≤ 1 MiB, `list` limit 1–1000 |
| Task / event payload | ≤ 1 MiB |
| Event topic | 1–100 characters (`A-Z a-z 0-9 . _ : -`) |
| `channel.messages()` | limit 1–100 |
| Component / modal ids | handler key ≤ 80 bytes; `c:<instance>:<id>` ≤ 100 bytes |
| Commands | name 1–32, description 1–100, ≤ 25 options, ≤ 25 choices |
| Portal links | default 15 min, max 24 h |
| `member.setNickname()` | ≤ 32 characters |
| `member.timeout()` | ≤ 28 days |

An uncaught error is logged with the instance and the revision. After three failures in a
row, the instance shows as `Degraded` in the status.

## 7. Type checking

Plugins are type-checked with a `tsconfig.json` that maps `@codi/sdk` to the SDK types:

- a scaffolded plugin uses `.codi/codi-sdk.d.ts` (`codi plugin sdk-types`);
- the examples use `spec/sdk/codi-sdk.d.ts`.

Use `"lib": ["ES2022"]` and `"types": []`, so that no DOM or Node types leak in. Run
`tsc --noEmit -p plugins/hello`.

## 8. Testing with `@codi/sdk/testing`

`@codi/sdk/testing` provides in-memory fakes that follow the SDK contract. They run in
Vitest or `node:test` without Discord:

- `createTestContext(options)` returns a harness. Its `ctx` goes to your handlers, and it
  records:
  - `sent` (messages with their `id`; DMs are `to: "dm:<userId>"`), `edits`,
    `deletedMessages`, `reactions`, `threads`;
  - `roleChanges`, `moderation` (timeouts, kicks, bans, nicknames);
  - `createdChannels` / `deletedChannels` (created channels resolve with `{ id }`, and
    `deleteChannel()` refuses channels the plugin did not create);
  - `links`, `published`, `scheduled`, `requests` (`http.fetch`), `logs`;
  - the raw `kv` (TTLs follow `Date.now()`, so `vi.useFakeTimers()` expires keys).

  It also offers `member(id)`, `addMember(init)`, `removeMember(id)`, `message(id)` and
  `channel(keyOrId)`. Options:
  - `config`, and `schema` (the plugin's `config.schema.json`): when given, its defaults are
    applied like the runtime does (`applyDefaults(schema, config)` is exported too);
  - `grants` (when given, calls without the grant throw `CapabilityError`);
  - `plugin`, `bot`, `server`, `roles` and `channels` (keyed by resource key), `members`,
    `portalUrl`;
  - `fetch(url, init)`: the fake `ctx.http.fetch` (`{ status?, headers?, body? }`).
- `callRoute(plugin, harness, "POST /complete", { viewer, body, query })` matches the
  route patterns. It answers `401` for anonymous callers of non-public routes and `403` for
  non-members of `member` routes, and returns `{ status, body, headers }`.
- `runCommand(plugin, harness, "name", { user, channel, options })`,
  `runComponent(plugin, harness, "vote:42", { user, message, values })` and
  `submitModal(plugin, harness, "open", { user, fields })` run interaction handlers with a
  fake interaction that follows the runtime's rules (a second `reply()` throws, `followUp()`
  needs a response, `showModal()` must come first, `update()` is for components; component
  and modal ids fall back to the part before `:`). They return
  `{ replies, followUps, updates, deferred, modal }`. `message` is a message sent through
  the fakes (or its id); `channel` sets `interaction.channel`.
- Events, tasks, schedules and subscriptions are plain functions: call them with the
  harness context, e.g. `await plugin.tasks!.close!(t.ctx, { id: "1" })`.
- `capabilityError(name)` and `normalizeRouteResponse(response)` are helpers.

In this repository, `pnpm test` runs `examples/**/test/**/*.test.ts` (root `vite.config.ts`);
`pnpm exec vp test examples/showcase/plugins/polls` runs one plugin's unit tests.
`codi plugin test <dir>` is different: it starts the plugin on the simulator with the real
runtime (no unit tests). To test a plugin end to end, run
`codi dev --sim` and drive it from the admin UI's **Simulator** panel
(`http://127.0.0.1:7420/admin/`): you can join members, send messages, run slash commands,
click buttons and submit modals.

## 9. Publishing: registries and the Store

Plugins are installed from **sources**, like apt sources or Homebrew taps (ADR-0011):
- **`codi`**, the official plugins bundled with the binary (welcome, onboarding, tickets,
  polls, levels, moderation). Always available.
- **Registries**: git repositories with an `index.yaml`, declared in `codi.yaml`
  `spec.registries`. They are **unofficial** (trust is computed from the URL, never
  declared): the admin UI labels them everywhere and asks for an explicit confirmation,
  showing the capabilities and network egress being granted, before installing from them.

To publish a plugin:
1. Put it in its own git repository (`plugin.yaml` at the root) and tag releases with
   semver tags (`v1.2.0`).
2. List it in a registry's `index.yaml`:
   ```yaml
   plugins:
     xp:
       repo: https://github.com/acme/codi-xp.git   # https registries may only list https repos
       displayName: XP & levels
       description: Levels and a portal leaderboard
       keywords: [xp, levels]
       publisher: acme
   ```
3. Users add the registry and install:
   ```sh
   codi registry add acme https://github.com/acme/codi-plugins.git
   codi registry search xp
   codi plugin add acme/xp --bot moderator
   ```
   or from the admin UI: **Store** → Sources → Add, then Install on a plugin.

Installing pins the version in `codi.lock` (commit + content hash) and adds
`source: acme/xp` with `version: ^1.2.0` to the bot. The admin UI installs exactly the
version that was reviewed: if a new tag appears between review and install, it asks to
review again. Before installation, the Store reads what an unofficial plugin requests from
its `plugin.yaml` only; its code (and so its slash commands) runs only once installed.

`codi registry list|add|remove|update|search` manages sources from the command line
(`file://` URLs and local paths are allowed there, for development registries; the admin
UI only accepts `https://`).
