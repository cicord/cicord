# Writing Cicord plugins

A Cicord plugin is a small TypeScript (or JavaScript) module that runs inside the runtime and
reacts to Discord: gateway events, slash commands, buttons and select menus, modals,
schedules, background tasks, events from other plugins and HTTP routes of the community
portal. Plugins have no Node.js APIs: every side effect goes through the `ctx` object, and
each call is checked against the capabilities that `bot.yaml` grants.

Normative references:

- [`spec/sdk/cicord-sdk.d.ts`](../spec/sdk/cicord-sdk.d.ts) is the `@cicord/sdk` API. The
  published `@cicord/sdk` package ships the same types.
- [`spec/README.md`](../spec/README.md) §4 covers plugin instances, §6 the manifest and
  capabilities, and §8 the SDK semantics.
- [`spec/schemas/plugin.schema.json`](../spec/schemas/plugin.schema.json) is the
  `plugin.yaml` schema.
- [`examples/basic/plugins/`](../examples/basic/plugins/) holds two complete plugins:
  `welcome` and `onboarding`.
- [`examples/showcase/`](../examples/showcase/) is a complete repository with seven
  production-grade plugins that together use the whole SDK: `tickets` (buttons, modals,
  plugin-owned private channels), `polls` (selects, buttons with data ids, live updates,
  tasks, cross-plugin events), `levels` (message content, reactions, role rewards, cron,
  public portal route), `moderation` (permissions, DMs, timeouts/kicks/bans, expiring KV,
  `http.fetch`), `reaction-roles` (role panels with buttons, a select menu or reactions,
  edited in place), `audit-log` (member and message events, subscriptions, batched posts)
  and `announcements` (time-zone schedules evaluated by a minute tick, `/announce` with a
  modal and tasks). [`docs/plugin-coverage.md`](plugin-coverage.md) maps every SDK feature
  to the plugin and the end-to-end test that exercise it.

## 1. Create a plugin

```sh
cicord plugin new plugins/hello        # scaffold (use --force to overwrite)
cicord plugin sdk-types plugins/hello  # (re)write .cicord/cicord-sdk.d.ts for editors and tsc
```

`cicord plugin new` writes:

```
plugins/hello/
├── plugin.yaml            # manifest (static, reviewed in PRs)
├── config.schema.json     # JSON Schema of the instance config
├── tsconfig.json          # maps "@cicord/sdk" to .cicord/cicord-sdk.d.ts
├── .cicord/cicord-sdk.d.ts    # the SDK types
├── src/
│   ├── index.ts           # export default definePlugin({...})
│   └── cicord-env.d.ts      # typed ctx.config (generated by `cicord plugin typegen`)
├── package.json           # unit tests only: "test": "node --test …"
├── test/hello.test.ts     # example unit test with @cicord/sdk/testing (§8)
├── vendor/cicord-sdk-*.tgz  # @cicord/sdk, embedded in the cicord binary (file: dependency)
└── .gitignore             # node_modules/
```

The unit tests work in any directory, inside or outside a Cicord repository, without npm
publication of `@cicord/sdk` (Node.js 24 runs the TypeScript tests directly):

```sh
cd plugins/hello && npm install && npm test     # or: pnpm install && pnpm test
```

The runtime ignores `package.json`, `test/` and `vendor/`: it bundles `src/` itself (§2).
Commit `vendor/` (36 KB). A `cicord` built without the portal kit (`go build` without
`make ui`) scaffolds the plugin without this test setup and says so.

The other plugin commands:

| Command | Purpose |
|---|---|
| `cicord plugin build <dir>` | Bundle the plugin the way the runtime does and check the definition against the manifest. |
| `cicord plugin typegen <dir>` | Generate `src/cicord-env.d.ts` (the typed `PluginConfig`) from `config.schema.json`. |
| `cicord plugin test <dir>` | Run the plugin on the Discord simulator with the real runtime: build, start, then a smoke test (a member joins, every command without required options is invoked). `--config` passes a config. Unit tests are separate (§8). |

Then enable the plugin on a bot in `bots/<bot>/bot.yaml`:

```yaml
spec:
  servers: [ma-commu]
  plugins:
    - name: welcome                 # instance key, unique within the bot
      source: ../../plugins/welcome # local path relative to bot.yaml (or <registry>/<plugin> + version)
      grants: [discord.messages.send, discord.channels.read, discord.members.read,
               discord.roles.assign, discord.dm.send, portal.links, storage.kv]
      config:
        channel: general
        autoRole: member
      overrides:
        ma-commu:
          config:                   # JSON merge patch (RFC 7386) over config
            message: "Salut {member}, bienvenue sur {server} !"
```

One **instance** runs per (bot, plugin instance, server). The same plugin can run twice under
two instance names with different configs, and `servers:` limits an instance to some of the
bot's servers. `cicord dev --sim` hot-reloads the plugin on every save. Use the admin UI's
**Simulator** panel to trigger events and commands without Discord.

## 2. Build model

The runtime bundles plugins itself with esbuild (Go library, no Node.js involved):

- The entry is `spec.entry`, which must `export default definePlugin({...})`.
- Every imported module is bundled in. Pure-JS npm libraries work; **Node.js built-ins**
  (`fs`, `path`, `node:*`, …) are refused at build time.
- `@cicord/sdk` is the only module resolved at run time (the host provides it).
- Target: ES2022, with async generators lowered. An inline source map is appended, so stack
  traces point at `src/index.ts:12:5`.
- At load time, the runtime checks the definition against the manifest:
  - a handler without its intent fails (§4);
  - `schedules`/`tasks` without `scheduler` fails;
  - `routes` without `portal.routes` fails;
  - `subscriptions` without `events.subscribe` fails.

  An unknown key in `definePlugin()`, an invalid command or an invalid cron expression is
  also a load error. The revision is then rejected, and the previous one keeps running.

## 3. Manifest (`plugin.yaml`)

```yaml
# yaml-language-server: $schema=../../../../spec/schemas/plugin.schema.json
apiVersion: cicord.dev/v1alpha1
kind: Plugin
metadata:
  name: welcome                    # key: lowercase, digits, '-'
  version: 0.1.0                   # semver
  displayName: Welcome             # ≤ 64 chars
  description: Greets new members… # ≤ 280 chars
  license: Apache-2.0              # also: authors, homepage, keywords (≤ 10)
spec:
  engine: ">=0.1.0"                # runtime versions this plugin supports
  entry: ./src/index.ts
  capabilities: [discord.messages.send, discord.channels.read, discord.members.read,
                 discord.roles.assign, discord.dm.send, portal.links, storage.kv]
  intents: [ServerMembers]
  config:
    schema: ./config.schema.json
  # network:                       # required when http.fetch is requested
  #   allow: [api.example.com, "*.example.org"]
```

The manifest is static and reviewable. Commands, handlers and routes come from the code.

### Capabilities and grants

Every capability in `spec.capabilities` must also be listed in the instance's `grants` in
`bot.yaml`. Otherwise `cicord validate` fails ("requests capabilities that are not granted"),
so a plugin update that asks for a new capability shows up in review. A call that is not
granted throws `CapabilityError` (its `capability` field names the missing one).

| Capability | Allows |
|---|---|
| `discord.messages.read` | `channel.messages()` (history) |
| `discord.messages.send` | `channel.send()`, `message.reply()` |
| `discord.messages.manage` | Edit/delete other authors' messages |
| `discord.reactions.manage` | `message.react()` |
| `discord.members.read` | `ctx.server.member()` |
| `discord.members.manage` | `member.setNickname()` |
| `discord.members.moderate` | `member.timeout()`, `kick()`, `ban()` |
| `discord.roles.assign` | `member.addRole()`, `removeRole()` |
| `discord.channels.read` | `ctx.server.channel()` |
| `discord.channels.manage` | `ctx.server.createChannel()` / `deleteChannel()` (plugin-owned channels) |
| `discord.threads.manage` | `channel.createThread()` |
| `discord.dm.send` | `member.send()` |
| `storage.kv` | `ctx.kv` |
| `scheduler` | `schedules`, `tasks`, `ctx.schedule` |
| `http.fetch` | `ctx.http.fetch()` to `spec.network.allow` hosts |
| `portal.routes` | `routes` |
| `portal.links` | `ctx.portal.link()` |
| `events.publish` / `events.subscribe` | `ctx.events.publish()` / `subscriptions` |

Answering the plugin's own interactions (`reply`, `defer`, `followUp`, `update`,
`showModal`) needs no capability.

**Isolation.** Each instance only reaches its own server. Channel IDs are checked to belong
to the instance's server, or to a DM channel the instance opened or received. Storage, tasks
and events are scoped to the instance or to its (bot, server).

**Network egress** (`http.fetch`). `spec.network.allow` takes public DNS hostnames with an
optional port. `*.example.com` matches subdomains, not `example.com` itself. IP literals,
`localhost` and reserved suffixes are rejected. On every request the runtime also:

- checks that every resolved address is public, and connects to the address it checked;
- re-checks every redirect hop (at most 5);
- allows only `https`.

`cicord dev` relaxes these checks: plain `http` and private addresses are allowed, so a
plugin can call a local service. See spec/README.md §6.

### Intents

Event handlers need gateway intents, which the manifest must declare:

| Handler | Intent |
|---|---|
| `memberJoin`, `memberLeave`, `memberUpdate` | `ServerMembers` (privileged) |
| `messageCreate`, `messageUpdate`, `messageDelete` | `ServerMessages` (add `MessageContent`, privileged, to read `message.content`) |

**Message content is gated per plugin.** A bot connects with the union of its plugins'
intents, but a plugin that does not declare `MessageContent` still gets an empty
`message.content` (and no `attachments`), in events and in `channel.messages()`, unless
the message is the bot's own, mentions the bot or is a DM. Declare `MessageContent` only
when the plugin reads what people write (e.g. `levels` ignores very short messages); a
plugin that only needs who posted and when (flood protection, ticket activity) does not.
| `reactionAdd`, `reactionRemove` | `ServerMessageReactions` |

A bot connects with the union of its plugins' intents, plus `spec.intents` and what the
reconciler needs (`AutoModerationConfiguration` when a server it lists declares
`spec.automod`, `ServerExpressions` for emojis, stickers and soundboard sounds, so that
hand edits of those reach selfHeal). Privileged intents must also be enabled in the Discord
developer portal: the runtime reads the application flags when the bot connects and, when
one is missing, does not open the gateway and reports which toggle to turn on in the bot
status.

## 4. Configuration

`config.schema.json` is JSON Schema 2020-12. The runtime checks each instance's config
against it, per server, after merging `overrides.<server>.config` into the base config.
Schema `default`s are applied before the plugin sees `ctx.config`: at the top level, in
nested objects, in every object element of arrays (e.g. `steps[].multiple`) and through
local `$ref`s. An absent optional object is created only when its defaults cover all its
`required` fields (so an optional `webhook: {url, format}` with a required `url` stays
absent). Defaults inside `additionalProperties` maps and `oneOf`/`anyOf` alternatives are
not applied. Cicord adds three keywords:

| Keyword | Values | Effect |
|---|---|---|
| `x-cicord-ref` | `channel`, `category`, `role` | The value is a resource key of the server (a string, or an array of strings). The admin UI renders a picker. `cicord validate` checks that the key exists on every server. |
| `x-cicord-widget` | `textarea`, `markdown`, `color`, `duration` | Rendering hint for the admin UI form. |
| `x-cicord-access` | `admin` (default), `moderator` | Who may edit the top-level field in the admin UI. Edits are written back to `bot.yaml` as a commit or a PR. |

From [`welcome/config.schema.json`](../examples/basic/plugins/welcome/config.schema.json):

```json
{
  "type": "object",
  "required": ["channel"],
  "properties": {
    "channel": { "type": "string", "x-cicord-ref": "channel" },
    "message": {
      "type": "string",
      "default": "Welcome {member} to {server}!",
      "x-cicord-widget": "textarea",
      "x-cicord-access": "moderator"
    },
    "autoRole": { "type": "string", "x-cicord-ref": "role" },
    "dmOnboarding": { "type": "boolean", "default": true }
  },
  "additionalProperties": false
}
```

`cicord plugin typegen` turns the schema into a module augmentation, so `ctx.config` is
typed. A field that is required, or has a default the runtime applies (rules above), is
non-optional:

```ts
// src/cicord-env.d.ts — generated, do not edit
declare module "@cicord/sdk" {
  interface PluginConfig {
    channel: string;
    message: string;
    autoRole?: string;
    dmOnboarding: boolean;
  }
}
export {};
```

Array items follow the same rule: with `"multiple": {"type": "boolean", "default": false}`
in `steps.items`, `ctx.config.steps[0].multiple` is a `boolean`, never `undefined`. Run
`cicord plugin typegen --check` in CI to catch a stale file.

## 5. The plugin definition

```ts
import { command, definePlugin } from "@cicord/sdk";

export default definePlugin({
  onStart(ctx) {},          // instance start (new revision, restart)
  onStop(ctx) {},           // before stop; bounded (3 s)
  events: {},               // gateway events
  commands: {},             // slash commands
  components: {},           // buttons / select menus
  modals: {},               // modal submissions
  schedules: {},            // cron jobs
  tasks: {},                // one-shot delayed jobs
  subscriptions: {},        // events from other plugins
  routes: {},               // community portal HTTP routes
});
```

Every handler receives `ctx`:

- `ctx.plugin` (`name`, `version`, `instance`), `ctx.bot` (`key`, `user`), `ctx.server`;
- `ctx.config` (effective config);
- `ctx.log`;
- `ctx.kv`, `ctx.schedule`, `ctx.http`, `ctx.events`, `ctx.portal`.

Server resources are referenced by their **key** in `servers/<server>.yaml`
(`ctx.server.channel("general")`, `member.addRole("member")`), or by `{ id }` for resources
Cicord does not manage.

#### Permission checks: roles, owner, access level

Discord checks a command's default `permissions` and the **bot's** role hierarchy, never
the invoker's. A plugin acting on behalf of a member (moderating someone, pinging a role)
checks the rest itself with:

- `role.position` (higher is higher, `@everyone` is 0) and `role.mentionable`;
- `ctx.server.ownerId` (read live, so an ownership transfer is seen at once);
- `member.permissions`: the **server-level** permissions (`@everyone` plus every role of
  the member; all of them for the owner and for `Administrator`). Channel overwrites and
  timeouts are **not** applied: it is not what the member may do in a given channel;
- `member.access`: the Cicord access level used by portal routes, `"admin"` for the owner
  and `spec.access.admins` of `servers/<server>.yaml`, `"moderator"` for
  `spec.access.moderators`, else `"member"`.

These fields are optional in the types: they are `undefined` when the runtime does not know
the value (a role not cached yet, an older engine). **Fail closed**: an unknown position or
access level must never let a check pass. The official `moderation` plugin is the
reference: the owner may moderate anyone, nobody may moderate the owner, staff (moderator
or admin access) can only be moderated by an admin, and the moderator's highest role must be
strictly above the target's; anything it cannot verify is refused.

### Events

From [`welcome`](../examples/basic/plugins/welcome/src/index.ts) (intent `ServerMembers`):

```ts
events: {
  async memberJoin(ctx, member) {
    const { channel, message, autoRole, dmOnboarding } = ctx.config;
    await ctx.server.channel(channel).send(render(message, { member: member.mention, server: ctx.server.name }));
    if (autoRole && !member.hasRole(autoRole)) await member.addRole(autoRole, "welcome: default role");
    if (dmOnboarding) {
      const url = await ctx.portal.link("/onboarding", { member });
      await member.send({ content: "Pick your roles:", components: [{ type: "row", components: [{ type: "link", label: "Start", url }] }] });
    }
    const total = await ctx.kv.increment("stats:joined");
    ctx.log.info("member welcomed", { member: member.id, total });
  },
},
```

The handlers are `memberJoin(member)`, `memberLeave(user)`, `memberUpdate(member, previous)`,
`messageCreate(message)`, `messageUpdate(message)`, `messageDelete({ id, channel })`,
`reactionAdd({ message, user, emoji })`, `reactionRemove(...)`, `serverJoin({ id, name,
iconUrl })` and `serverLeave({ id })`. The `message` of a reaction is partial (fetch it with
`message.channel.message(message.id)` when you need its content). Events are delivered in
order for each instance.

`serverJoin` / `serverLeave` need no intent (Servers is always enabled). `serverJoin` fires
when the bot joins a server while connected (an invite accepted, for instance after it was
removed), not for servers that load after a connection or recover from an outage;
`serverLeave` fires when the bot is kicked, banned, removed or the server is deleted, not
during a Discord outage. Like every event, they only reach the instances of servers declared
for the bot in `bot.yaml`: joining an undeclared server runs no plugin. After a re-invite the
runtime also registers the slash commands of the server again.

### Commands

Commands are keyed by name (lowercase letters, digits, `-` and `_`, 1–32 characters) and
synced to each server. The `command()` helper infers the type of `interaction.options`.
From `welcome`:

```ts
commands: {
  "welcome-preview": command({
    description: "Preview the welcome message", // 1–100 characters
    ephemeral: true,                             // ephemeral replies and auto-defer
    permissions: ["ManageServer"],               // default member permissions
    options: {
      member: { type: "user", description: "Member to greet (defaults to you)" },
    },
    async run(ctx, interaction) {
      const target = interaction.options.member ?? interaction.user; // User | undefined
      await interaction.reply({ content: render(ctx.config.message, { member: target.mention, server: ctx.server.name }), ephemeral: true });
    },
  }),
},
```

The rules for options:

- `type` is one of `string`, `integer`, `number`, `boolean`, `user`, `channel`, `role`,
  `mentionable` or `attachment`.
- `required` options come first in Discord.
- `min`/`max` only apply to `integer`/`number`.
- `minLength`/`maxLength` only apply to `string` (0–6000; `maxLength` ≥ 1).
- `choices` (≤ 25) only apply to `string`/`integer`/`number`.
- `autocomplete` (a function) only applies to `string`/`integer`/`number`, and not together
  with `choices` (see below).
- A command takes at most 25 options.

#### Subcommands and groups

A command can be made of **subcommands** (`/polls close`, `/polls results`), optionally
organised in **groups** (`/polls admin purge`). `subcommand()` types the options of each one
like `command()` does; `interaction.subcommand` and `interaction.group` tell which one runs.
From [`polls`](../examples/showcase/plugins/polls/src/index.ts):

```ts
import { command, subcommand } from "@cicord/sdk";

commands: {
  polls: command({
    description: "Manage polls",
    ephemeral: true,                    // applies to every subcommand, like permissions
    subcommands: {
      close: subcommand({
        description: "Close a poll now",
        options: { poll: { type: "string", description: "Poll", required: true, autocomplete: suggestPolls } },
        async run(ctx, interaction) {    // interaction.subcommand === "close"
          const poll = await getPoll(ctx, interaction.options.poll);
          …
        },
      }),
    },
    groups: {
      admin: { description: "Administration", subcommands: { purge: subcommand({ description: "…", run() {} }) } },
    },
  }),
},
```

Discord's rules, checked when the plugin is built:

- a command with `subcommands`/`groups` has no `run` and no `options` of its own (it cannot be
  invoked alone);
- at most 25 subcommands and groups per command, with distinct names;
- a group holds 1–25 subcommands and nothing else; subcommands do not nest further.

#### Autocomplete

An option with `autocomplete` gets suggestions while the user types it. The handler receives
`ctx`, the `AutocompleteInteraction` (user, member, channel, `command`/`group`/`subcommand`
and the raw values of the other options already filled in) and the focused option
`{ name, value }`, where `value` is the text typed so far (a string, even for `integer` and
`number` options). It returns at most 25 `{ name, value }` choices (names 1–100 characters,
values of the option's type, strings ≤ 100 characters):

```ts
options: {
  poll: {
    type: "string", description: "Poll", required: true,
    async autocomplete(ctx, interaction, focused) {
      const polls = await listPolls(ctx);
      return polls
        .filter((p) => p.question.toLowerCase().includes(focused.value.toLowerCase()))
        .slice(0, 25)
        .map((p) => ({ name: `#${p.id} ${p.question}`, value: p.id }));
    },
  },
},
```

Suggestions are only suggestions: the user may still send any text, so `run` validates the
value. An autocomplete cannot be deferred: Discord drops answers after 3 s, so the runtime
gives the handler **2.5 s**. A handler that throws, is late or returns invalid choices shows
an empty list (the error is logged).

### Interactions: reply, defer, follow up

Discord expects an answer within 3 s. If a handler has not answered after **2 s**, the
runtime defers the interaction automatically:

- the deferral is ephemeral when the command says `ephemeral: true`;
- components get a silent "deferred update".

A later `reply()` then edits the deferred response. The first response fixes ephemerality.
After `reply()`, use `followUp()`. Autocomplete interactions are the exception: they are
never deferred, the handler's return value is the answer. If a handler throws before answering, the user gets an
ephemeral *"Something went wrong while handling this interaction."*, and the error is logged.

| State | `reply()` | `defer()` | `update()` (components) | `followUp()` | `showModal()` |
|---|---|---|---|---|---|
| unanswered | initial reply | defers | edits the component's message | error | opens the modal |
| deferred (command/modal) | edits the deferred reply | no-op | error | follow-up | error |
| deferred (component) | follow-up | no-op | edits the message | follow-up | error |
| updated | follow-up | error | edits the message | follow-up | error |
| replied | error (use `followUp`) | error | error | follow-up | error |

### Components and modals

Component and modal `id`s are local to the plugin instance. On the wire the runtime
namespaces them as `c:<instance>:<id>`, which must fit Discord's 100-byte `custom_id`
limit. Handler keys are at most 80 bytes. An id may **carry data after a colon**: the lookup
falls back to the part before the first `:`, so `"vote:42"` is routed to `components.vote`,
and `componentId` stays `"vote:42"`. A sketch (`examples/showcase/plugins/polls` and
`tickets` are complete examples):

```ts
commands: {
  poll: command({
    description: "Start a poll",
    async run(ctx, interaction) {
      await interaction.reply({
        content: "Ready?",
        components: [{ type: "row", components: [
          { type: "button", id: "vote:yes", label: "Yes", style: "success" },
          { type: "button", id: "feedback", label: "Feedback…" },
        ] }],
      });
    },
  }),
},
components: {
  async vote(ctx, interaction) {           // receives "vote:yes"
    const [, answer] = interaction.componentId.split(":");
    await ctx.kv.increment(`poll:${answer}`);
    await interaction.update({ content: `Thanks, ${interaction.user.displayName}!`, components: [] });
  },
  async feedback(ctx, interaction) {
    await interaction.showModal({
      id: "feedback", title: "Feedback",
      fields: [{ id: "text", label: "Your feedback", style: "paragraph", required: true, maxLength: 500 }],
    });
  },
},
modals: {
  async feedback(ctx, interaction) {
    ctx.log.info("feedback", { text: interaction.fields.text ?? "" });
    await interaction.reply({ content: "Thanks!", ephemeral: true });
  },
},
```

Select menus are `{ type: "select", id, options: [{ value, label }], minValues?, maxValues? }`,
and the picked values arrive in `interaction.values`. Link buttons are
`{ type: "link", url, label }` and trigger no handler.

### Mentions: `allowedMentions`

Without `allowedMentions`, every mention in the content notifies, including roles that are
not mentionable when the bot has MentionEveryone. Set it whenever the content contains text
from a member, or a mention the member picked:

```ts
await channel.send({
  content: `${role.mention} — new poll by ${interaction.user.mention}`,
  // Notifies exactly this role: not the author, not any other mention in the text.
  allowedMentions: { roles: [role.id], users: [] },
});
```

`users` and `roles` take `true` (every mention of that type), `false` (none) or a list of
**ids** (snowflakes, not resource keys) or objects with an `id` (a `User`, `Member` or
`Role`), at most 100 per list; a type cannot be both allowed and listed. `everyone` allows
`@everyone` / `@here`; `repliedUser` notifies the author of the message replied to
(`message.reply()`). A non-mentionable role, `@everyone` and `@here` still only notify
when the bot has MentionEveryone in the channel. Invalid lists make the call throw. The
official `polls` plugin only lets poll managers ping a role that is not mentionable, and
notifies only the picked member or role.

### Portal routes

`routes` expose JSON endpoints under
`/api/v1/portal/{server}/plugins/{bot}/{instance}/{path}` (spec/api.md §6). They need
`portal.routes`. Keys are `"<GET|POST|PUT|PATCH|DELETE> /path"`, and `:name` segments are
parameters (`request.params`).

`access` is required: `public`, `member`, `moderator` or `admin`. The runtime enforces it:
anonymous callers get `401`, and an insufficient role gets `403`. The handler receives:

- `request.viewer` (`{ user, member }`);
- `request.query` (the first value of each parameter);
- `request.body` (JSON).

A handler can return:

- any JSON value (`200`);
- an envelope `{ status, body?, headers? }`;
- nothing, which answers `204`.

A handler that returns both envelopes and plain JSON objects should declare its return type
(`async handler(ctx, request): Promise<RouteResponse>`): TypeScript otherwise infers a union
that does not match `RouteResponse`. Interfaces are not assignable to `Json` (no index
signature): cast records with `as unknown as Json`.

From [`onboarding`](../examples/basic/plugins/onboarding/src/index.ts):

```ts
routes: {
  "GET /steps": {
    access: "member",
    async handler(ctx, request) {
      const member = request.viewer?.member;
      if (!member) return { status: 403, body: { error: { code: "forbidden", message: "members only" } } };
      const record = await ctx.kv.get<CompletionRecord>(completionKey(member.id));
      return resolveSteps(ctx, member, record);
    },
  },
},
```

#### Typed routes: the route contract

A plugin can declare the types of its routes, so that portals get a typed client for them
(`cicord portal typegen`, [docs/portal.md](portal.md#typed-plugin-routes)) and its handlers
are checked against them. Write a **route contract**: a type-only, self-contained file
(no imports, only `interface` and `type` declarations, since it is copied verbatim into
the portals) that exports `interface Routes`, and declare it in `plugin.yaml`:

```yaml
spec:
  routes:
    types: ./src/routes.ts
```

```ts
// src/routes.ts
export interface PollResults { id: string; question: string; voters: number }

export interface Routes {
  "GET /polls/:id": { response: PollResults };                 // params come from the key
  "GET /polls": { query: { status?: "open" | "closed" }; response: { items: PollResults[] } };
  "POST /polls/:id/votes": { body: { choice: number }; response: { votes: number } };
  "DELETE /polls/:id": {};                                     // no response: 204
}
```

Then wrap the routes with `defineRoutes<Routes>()` (identity at run time):

```ts
import { definePlugin, defineRoutes } from "@cicord/sdk";
import type { Routes } from "./routes.ts";

export default definePlugin({
  routes: defineRoutes<Routes>({
    "GET /polls/:id": {
      access: "public",
      async handler(ctx, request) {
        const poll = await getPoll(ctx, request.params.id); // params: { id: string }
        if (!poll) return { status: 404, body: { error: { code: "not_found", message: "no such poll" } } };
        return toResults(poll); // checked against PollResults
      },
    },
    // … every route of Routes must be implemented
  }),
});
```

`request.params` is typed from the key, `request.query` has the declared keys (as the
strings of the URL), `request.body` is the declared body, and the handler must return the
declared `response` or an envelope `{ status, body?, headers? }`. The runtime does **not**
validate the query or the body against the types: check them like any input. Interfaces
can be returned directly (no `as unknown as Json`). `cicord plugin build` reports a contract
that cannot be copied (an import, a value…). [`levels`](../examples/showcase/plugins/levels/src/routes.ts)
and [`polls`](../examples/showcase/plugins/polls/src/routes.ts) are examples.

`ctx.portal.link(path, { member, expiresInSeconds })` (capability `portal.links`) returns a
signed portal URL. With `member`, opening it signs that member in, restricted to this server.
Links last 15 minutes by default, 24 hours at most. In the portal, `@cicord/client`'s
`client.routes(plugin, server, instance)` / `client.plugin(server, bot, instance)` and
`@cicord/react`'s `useRouteQuery` / `usePluginQuery` call the routes.

### Schedules and tasks

Both need `scheduler`. `schedules` run on a cron expression in **UTC**. Standard 5-field
cron and descriptors (`@hourly`, `@daily`, `@every 10m`) are accepted. `TZ=` prefixes are
refused. `tasks` are one-shot jobs started with `ctx.schedule.after()`. They are persisted,
so they survive restarts.

```ts
schedules: {
  digest: { cron: "0 9 * * 1", async run(ctx) {
    await ctx.server.channel("announcements").send("Weekly digest…");
  } },
},
tasks: {
  async remind(ctx, payload) {
    const { userId } = payload as { userId: string };
    await (await ctx.server.member(userId))?.send("Reminder!");
  },
},
// elsewhere: const { id } = await ctx.schedule.after(60 * 60_000, "remind", { userId });
//            await ctx.schedule.cancel(id);
```

A task often has to edit a message posted earlier (e.g. close a poll): post with
`channel.send()` (which returns the `Message`), store `{ channelId, messageId }`, and in the
task fetch it back with `ctx.server.channel({ id: channelId }).message(messageId)`
(capability `discord.messages.read`; `undefined` when the message was deleted).
`examples/showcase/plugins/polls` does this.

### Plugin-owned channels

`ctx.server.createChannel({ name, type, category, topic, overwrites })`
(`discord.channels.manage`) creates a channel recorded as owned by the plugin instance: the
reconciler never touches or prunes it, even with `prune: true`, and only that instance can
`deleteChannel()` it. `overwrites` keys are `"@everyone"`, a role key, `"role:<id>"` or
`"member:<id>"`. Give the bot itself access (`member:${ctx.bot.user.id}`) when the channel
hides `@everyone`, or a bot without Administrator locks itself out. See
`examples/showcase/plugins/tickets`.

### Cross-plugin events

`ctx.events.publish(topic, payload)` (`events.publish`) delivers to the instances of the same
(bot, server). Topics are namespaced with the publisher's plugin name, so plugin `xp` calling
`publish("levelUp", …)` reaches `subscriptions["xp.levelUp"]` (`events.subscribe`).

```ts
// plugin "xp"
await ctx.events.publish("levelUp", { userId: member.id, level: 5 });
// another plugin
subscriptions: {
  async "xp.levelUp"(ctx, payload) {
    const { userId, level } = payload as { userId: string; level: number };
    ctx.log.info("level up", { userId, level });
  },
},
```

### Storage, HTTP, logging

- `ctx.kv` (`storage.kv`) is a JSON key-value store scoped to the instance, with these
  operations:
  - `get`;
  - `set(key, value, { ttlSeconds })`;
  - `delete`;
  - atomic `increment`;
  - `list({ prefix, limit, cursor })`.
- `ctx.http.fetch(url, { method, headers, body, timeoutMs })` (`http.fetch`) returns
  `{ status, headers, text(), json() }`.
- `ctx.log.debug/info/warn/error(message, fields)` and `console.*` go to the runtime log,
  tagged with the plugin instance.

### Globals

Plugins get `setTimeout`, `setInterval`, `clearTimeout`, `clearInterval`, `queueMicrotask`
and `console`. Timers belong to the handler that created them and stop with it. There is no
`process`, `fetch`, DOM or Node.js API.

## 6. Execution model and limits

Each plugin instance gets its own VM and one event loop: QuickJS-ng compiled to
WebAssembly, run in the Cicord process by wazero (ADR-0018). Handlers interleave at `await`
points, like in Node.

| Limit | Value |
|---|---|
| Synchronous JS per event-loop turn | 50 ms (a runaway turn aborts the handler; the instance keeps running) |
| Memory per instance | 64 MiB of JavaScript heap; reaching it discards the instance (even if the error is caught), which restarts with backoff (1 s, doubling up to 5 min) |
| Code that ignores the turn budget (a long native call) | killed 500 ms after the budget (one more budget for budgets above 500 ms); the instance restarts |
| Microtasks still spinning after their handler was aborted | the instance restarts |
| Pending SDK calls per instance | 256 (beyond, the call rejects) |
| Handler calls waiting for the instance | 1024 (beyond, the call fails as busy) |
| SDK call arguments | ≤ 2 MiB of JSON; `ctx.log` fields ≤ 16 KiB (larger ones are dropped) |
| Module evaluation at start | 2 s |
| Handler duration, awaits included | 10 s (async work it started is cut too) |
| Auto-defer of interactions | 2 s |
| Autocomplete handlers | 2.5 s, never deferred; ≤ 25 choices (name 1–100, string values ≤ 100) |
| `onStop` | 3 s |
| `http.fetch` | 10 s default timeout (`timeoutMs` up to the handler timeout), response ≤ 5 MiB, request body ≤ 1 MiB, ≤ 5 redirects |
| KV | key 1–512 bytes, value ≤ 1 MiB, `list` limit 1–1000 and ≤ 4 MiB per page (a larger page is cut short; its `cursor` continues) |
| Portal route response | ≤ 4 MiB of JSON |
| Task / event payload | ≤ 1 MiB |
| Event topic | 1–100 characters (`A-Z a-z 0-9 . _ : -`) |
| `channel.messages()` | limit 1–100 (`channel.message(id)` fetches one) |
| Component / modal ids | handler key ≤ 80 bytes; `c:<instance>:<id>` ≤ 100 bytes |
| Commands | name 1–32, description 1–100, ≤ 25 options, ≤ 25 choices, ≤ 25 subcommands and groups (a group holds ≤ 25 subcommands), string options ≤ 6000 characters (`minLength`/`maxLength`) |
| Portal links | default 15 min, max 24 h |
| `member.setNickname()` | ≤ 32 characters |
| `member.timeout()` | ≤ 28 days |

An uncaught error is logged with the instance and the revision. After three failures in a
row, the instance shows as `Degraded` in the status. A crashed instance (memory limit, killed
code) shows as `Degraded` at once with the reason, and is restarted automatically: while it
restarts, its calls fail and interactions get the generic error reply.

## 7. Type checking

Plugins are type-checked with a `tsconfig.json` that maps `@cicord/sdk` to the SDK types:

- a scaffolded plugin uses `.cicord/cicord-sdk.d.ts` (`cicord plugin sdk-types`);
- the examples use `spec/sdk/cicord-sdk.d.ts`.

Use `"lib": ["ES2023"]` (the engine provides the ES2023 built-ins, such as `toSorted` and `findLast`) and `"types": []`, so that no DOM or Node types leak in. Run
`tsc --noEmit -p plugins/hello`.

## 8. Testing with `@cicord/sdk/testing`

`@cicord/sdk/testing` provides in-memory fakes that follow the SDK contract. They run in
Vitest or `node:test` without Discord:

- `createTestContext(options)` returns a harness. Its `ctx` goes to your handlers, and it
  records:
  - `sent` (messages with their `id` and, when set, the normalized `allowedMentions`: lists
    hold ids; DMs are `to: "dm:<userId>"`), `edits`,
    `deletedMessages`, `reactions`, `threads`;
  - `roleChanges`, `moderation` (timeouts, kicks, bans, nicknames);
  - `createdChannels` / `deletedChannels` (created channels resolve with `{ id }`, and
    `deleteChannel()` refuses channels the plugin did not create);
  - `links`, `published`, `scheduled`, `requests` (`http.fetch`), `logs`;
  - the raw `kv` (TTLs follow `Date.now()`, so `vi.useFakeTimers()` expires keys).

  It also offers `member(id)`, `addMember(init)`, `removeMember(id)`, `message(id)` and
  `channel(keyOrId)`. Options:
  - `config`, and `schema` (the plugin's `config.schema.json`): when given, its defaults are
    applied like the runtime does (`applyDefaults(schema, config)` is exported too);
  - `grants` (when given, calls without the grant throw `CapabilityError`);
  - `plugin`, `bot`, `server`, `roles` and `channels` (keyed by resource key), `members`,
    `portalUrl`;
  - for permission checks: roles take `position` (default 1, 2, 3… in declaration order),
    `mentionable` and `permissions`; `server` takes `ownerId` and `everyonePermissions`;
    `access: { admins, moderators }` (`{ users?, roles? }`, role keys) sets
    `member.access`. `member.permissions` is computed like the runtime (server-level);
  - `fetch(url, init)`: the fake `ctx.http.fetch` (`{ status?, headers?, body? }`).
- `callRoute(plugin, harness, "POST /complete", { viewer, body, query })` matches the
  route patterns. It answers `401` for anonymous callers of non-public routes and `403` for
  non-members of `member` routes, and returns `{ status, body, headers }`.
- `runCommand(plugin, harness, "name", { user, channel, options })`,
  `runComponent(plugin, harness, "vote:42", { user, message, values })` and
  `submitModal(plugin, harness, "open", { user, fields })` run interaction handlers with a
  fake interaction that follows the runtime's rules (a second `reply()` throws, `followUp()`
  needs a response, `showModal()` must come first, `update()` is for components; component
  and modal ids fall back to the part before `:`). They return
  `{ replies, followUps, updates, deferred, modal }`. `message` is a message sent through
  the fakes (or its id); `channel` sets `interaction.channel`. For a command with
  subcommands, `runCommand` takes the path: `"polls close"`, `"polls admin purge"`.
- `runAutocomplete(plugin, harness, "polls close", { user, focused: "poll", value: "piz",
  options })` runs the option's `autocomplete` handler and returns its choices, checked like
  the runtime checks them (an invalid result throws).
- Events, tasks, schedules and subscriptions are plain functions: call them with the
  harness context, e.g. `await plugin.tasks!.close!(t.ctx, { id: "1" })`.
- `capabilityError(name)`, `normalizeRouteResponse(response)` and
  `normalizeAllowedMentions(message)` are helpers. Sent messages, replies, follow-ups and
  updates check `allowedMentions` like the host (ids must be snowflakes or ids of the
  fakes, such as `role-staff`).

Adapted from [`onboarding.test.ts`](../examples/basic/plugins/onboarding/test/onboarding.test.ts):

```ts
import { callRoute, createTestContext, runCommand } from "@cicord/sdk/testing";
import { expect, test } from "vite-plus/test";
import schema from "../config.schema.json" with { type: "json" };
import plugin from "../src/index.ts";

const t = createTestContext({
  config,
  schema, // the runtime's defaults (steps[].multiple…)
  grants: ["discord.roles.assign", "storage.kv", "portal.routes", "portal.links"],
  roles: { pc: { name: "PC" }, member: { name: "Membre" } },
  members: [{ id: "1", username: "alice", roles: ["pc"] }],
});

test("GET /steps", async () => {
  const res = await callRoute(plugin, t, "GET /steps", { viewer: "1" });
  expect(res.status).toBe(200);
});

test("/onboarding replies with a link", async () => {
  const r = await runCommand(plugin, t, "onboarding", { user: "1" });
  expect(r.replies).toHaveLength(1);
});
```

Importing the JSON schema needs `"resolveJsonModule": true` in the test `tsconfig.json`.

**Outside this repository**, `cicord plugin new` sets the tests up with `node:test` (no other
dependency than the vendored `@cicord/sdk`, see §1): `npm test` runs `test/**/*.test.ts`
with Node 24's type stripping, so keep the sources strippable (`.ts` extensions on
relative imports, `import type` for types, no `enum`/`namespace`). Use `node:assert`
instead of `expect`; anything else from the examples applies. Prefer Vitest? `npm i -D
vitest` and replace the test script with `vitest run`. Once `@cicord/sdk` is on npm, replace
`"file:vendor/cicord-sdk-….tgz"` with `"^0.1.0"` and delete `vendor/`.

In this repository, `pnpm test` runs `examples/**/test/**/*.test.ts` (root `vite.config.ts`);
`pnpm exec vp test examples/showcase/plugins/polls` runs one plugin's unit tests.
`cicord plugin test <dir>` is different: it starts the plugin on the simulator with the real
runtime (no unit tests). To test a plugin end to end, run
`cicord dev --sim` and drive it from the admin UI's **Simulator** panel
(`http://127.0.0.1:7420/admin/`): you can join members, send messages, run slash commands,
click buttons and submit modals.

## 9. Publishing: registries and the Store

Plugins are installed from **sources**, like apt sources or Homebrew taps (ADR-0011):
- **`cicord`**, the official plugins bundled with the binary (welcome, onboarding, tickets,
  polls, levels, moderation, reaction-roles, audit-log, announcements). Always available.
  `cicord` also lists the plugins of the official registry,
  [github.com/cicord/cicord-plugins](https://github.com/cicord/cicord-plugins), when its
  signed index verifies (see *The official registry* below), without any `cicord.yaml`
  entry.
- **Registries**: git repositories with an `index.yaml`, declared in `cicord.yaml`
  `spec.registries`. They are **unofficial** (trust is computed from the URL, never
  declared): the admin UI labels them everywhere and asks for an explicit confirmation,
  showing the capabilities and network egress being granted, before installing from them.

To publish a plugin:
1. Put it in its own git repository (`plugin.yaml` at the root), commit, and release it
   with `cicord plugin publish` (below), or tag releases by hand with semver tags (`v1.2.0`).
   A repository can also hold several plugins (a monorepo, like the official registry):
   each plugin is a directory (`plugins/xp/plugin.yaml`) released with its own tags,
   `<name>/v<semver>` (`xp/v1.2.0`).
2. List it in a registry's `index.yaml`:
   ```yaml
   plugins:
     xp:
       repo: https://github.com/acme/cicord-xp.git   # https registries may only list https repos
       # path: plugins/xp   # in a monorepo: the plugin directory (tags xp/v<semver>)
       displayName: XP & levels
       description: Levels and a portal leaderboard
       keywords: [xp, levels]
       publisher: acme
       version: 1.2.0     # latest release (written by publish)
       commit: 3f1c…      # its tag's commit: resolving 1.2.0 fails if the tag moved
   ```
3. Users add the registry and install:
   ```sh
   cicord registry add acme https://github.com/acme/cicord-plugins.git
   cicord registry search xp
   cicord plugin add acme/xp --bot moderator
   ```
   or from the admin UI: **Store** → Sources → Add, then Install on a plugin.

For a plugin with a `path`, only its directory is downloaded, and the content hash covers
that directory (paths relative to it, so a plugin hashes the same in its own repository and
in a monorepo); bare `v<semver>` tags and the tags of the other plugins are ignored. A
`path` is a relative directory (no `..`, no leading `/`, no hidden segments).

Installing pins the version in `cicord.lock` (commit + content hash, and `path`) and adds
`source: acme/xp` with `version: ^1.2.0` to the bot. The admin UI installs exactly the
version that was reviewed: if a new tag appears between review and install, it asks to
review again. Before installation, the Store reads what an unofficial plugin requests from
its `plugin.yaml` only; its code (and so its slash commands) runs only once installed.

**Private registries.** A registry can require an access token (a private GitHub/GitLab
repository). Give the token in the admin UI (Store → Sources), or declare
`secretRef: CICORD_REGISTRY_ACME_TOKEN` in `cicord.yaml` (`cicord registry add acme <url> --private`)
and provide it as an environment variable or with `cicord secret set`. The secret name is
always `CICORD_REGISTRY_<NAME>_TOKEN` for the registry's own name, so a `cicord.yaml` edit can
never send another secret (a bot token, another registry's token) to a registry host. `cicord.yaml` only stores the secret's name. The token is sent to the
registry's host only (its index and the plugin repositories on that host).

**Updating.** Publishing a new tag is all it takes: Cicord compares each `cicord.lock`
version with the highest release tag of the plugin repository (any major version) and
shows "Update available" in the Store, the Plugins table and on the plugin's page. The
update review shows what the new version requests compared with the installed one
(capabilities, gateway intents — privileged ones highlighted —, network hosts), what it
changes for each instance (version range, grants) and whether their current settings are
still valid with the new config schema. Updating rewrites the lock entry, widens the
instances' version range when the new version is outside it (`^1.0.0` → `^2.0.0`) and sets
their grants to what the new version requests, for every instance at once (the version is
shared), so it needs the admin role on every server where the plugin runs. Unofficial
sources ask again for an explicit confirmation restating what is newly granted. As for
installs, the code updated to is the code that was reviewed (`409 changed` otherwise).
From the command line:
```sh
cicord plugin update                       # list available updates
cicord plugin update acme/xp               # update to the latest version, print the diff
cicord plugin update acme/xp --to ~1.3.0   # or within a range (written to every instance)
```
What this means for publishers: keep the settings of a minor version compatible (a new
required field makes every existing instance invalid, and the update is refused until
admins fix it), and release breaking changes as a new major version. New capabilities,
intents or network hosts are shown to admins as such before they update.

Copies of the bundled official plugins (`plugins/<name>/`) update from the binary: a newer
Cicord version may bundle a newer version. A copy changed in your repository is not
overwritten unless you force it (admin UI checkbox, `cicord plugin update cicord/<name> --force`).

**Uninstalling** from the admin UI (a plugin's page → Uninstall) removes the instance from
the bot; when no other instance uses the plugin, its `cicord.lock` entry or its copied
`plugins/<name>/` directory goes too. Its stored data is kept.

`cicord registry list|add|remove|update|search` manages sources from the command line
(`file://` URLs and local paths are allowed there, for development registries; the admin
UI only accepts `https://`).

### `cicord plugin publish`

Run it in the plugin's repository when `metadata.version` in `plugin.yaml` is the version
to release:

```sh
cicord plugin publish --dry-run                       # check everything, change nothing
cicord plugin publish --push --registry ../cicord-plugins --publisher acme
cicord plugin publish plugins/xp --push --registry .  # a monorepo that is its own registry
```

It
1. builds and inspects the plugin like `cicord plugin build` (any error stops it);
2. refuses a dirty working tree (the tag must point at the code that was validated), a
   `metadata.name` that is not a valid registry key, and a version that is not a semver
   greater than every existing tag (local tags; with `--push`, the remote's too);
3. creates the annotated tag `v<version>` on `HEAD`, and pushes it with `--push` (to
   `--remote`, default `origin`, with your git credentials);
   in a monorepo (the plugin directory is not the repository root, or `--path <dir>`
   names it from the root) the tag is `<name>/v<version>`, the version is compared with
   that plugin's tags only, only its directory must be clean, and the entry gets
   `path: <dir>`;
4. computes the index entry: `repo` from `--repo` or the remote URL (`git@host:a/b.git`
   becomes `https://host/a/b.git`; URLs with credentials are refused), `displayName`,
   `description` and `keywords` from `plugin.yaml`, `publisher`, `version` and `commit`.
   With `--registry <dir>` (a local checkout of the registry repository) it adds or
   updates the entry in that `index.yaml`, keeping comments and the fields it does not
   manage; an existing entry keeps its `verified` flag and `publisher`, and its `repo`
   and `path` only change with `--replace-repo`. Then commit there and open a pull request. Without
   `--registry` (or with an https URL) it prints the entry and the steps.

Everything is checked before the tag is created. `publish` never sets `verified`:
registry maintainers do. If the registry's index is signed (`index.yaml.sig`), it warns
that the signature is now stale: the maintainers sign again after merging.

### The official registry: signed index, verified publishers

The official registry is
[github.com/cicord/cicord-plugins](https://github.com/cicord/cicord-plugins), a monorepo
maintained by the Cicord project: `plugins/<name>/` for each official plugin (tags
`<name>/v<semver>`), `index.yaml` at the root listing them with `path`, and community
plugins accepted by review (verified publishers). Its `index.yaml` is **signed**: `index.yaml.sig`, next to it, is a signature envelope followed
by one ed25519 signature per signing key:

```
# Signatures of index.yaml (cicord registry sign). Do not edit.
format: cicord-registry-signature-v1
registry: https://github.com/cicord/cicord-plugins   # normalized URL of the registry
serial: 1764000000                               # increases with every signature
expires: 2026-12-23T00:00:00Z                    # the signature is refused after this
index-sha256: 9f86d081…                          # SHA-256 of the exact bytes of index.yaml
ed25519 <key-id> <base64 signature>
```

Each signature covers the canonical envelope (the five fields, in this order, as
`name: value` lines after the format line), so it binds the index content to one registry,
one serial and one expiry. The runtime only uses an index read from an official URL when:
- a signature by one of the official public keys embedded in the binary (a list, for
  rotation) verifies, and the hash matches `index.yaml`;
- `registry` is the official registry's URL (a signature made for another registry, e.g.
  a staging copy, is refused);
- it has not expired;
- `serial` is not lower than the highest serial this runtime has already seen for the
  official registry (trust on first use, stored in the runtime's state database so it
  survives restarts; the CLI keeps it next to its plugin cache). All official URLs
  (aliases, mirrors) share this one serial. An older, validly signed index replayed by a
  mirror or an attacker, through any official URL, is refused.

Otherwise the source is an **error** source (`signature: "invalid"`): no plugins are
listed or installable from it, and it is never downgraded to an unofficial source with its
`verified` flags. `verified: true` (a verified publisher) is only honoured from a verified
official index; in any other registry it is ignored.

**Maintainers.**
- `cicord registry keygen --out <file>` creates a key pair (the private key file is mode
  0600 and never overwritten; keep it out of any repository) and prints the public key to
  embed in the runtime (`internal/registry` `OfficialKeys`).
- `cicord registry sign <checkout> --key <file> --registry-url <official URL>` (or
  `--key env:NAME` to read the key from an environment variable, e.g. a CI secret) writes
  `index.yaml.sig`; commit both files together. The serial defaults to the current Unix
  time (always above the previous one), the validity to 30 days (`--expires-in`, at most
  180 days).
- **Re-sign after every change to `index.yaml`, and on a schedule**: a weekly CI job that
  signs again (new serial, new 30-day expiry) keeps the signature valid with three weeks
  of margin. If it lapses, runtimes stop listing the official registry's plugins (the
  bundled ones remain) until it is signed again.
- `cicord registry verify <checkout> [--public-key <b64>] [--registry-url <url>]` checks the
  signature, hash, registry and expiry, for the registry's CI.
- Key rotation: embed the new public key, sign with both keys (`--key old --key new`)
  until runtimes trusting only the old key are gone, then drop it.
- Serials only go up: `sign` refuses a `--serial` not above the current one, or more than
  a year above the current Unix time (runtimes would then refuse every later signature).
  If a wrong serial was ever published, a runtime recovers by deleting the key `official`
  of the KV scope `cicord:registry-serials` in its state database (the CLI: the
  `registry-serials.json` file next to its plugin cache).

**Implicit official registry.** The official registry needs no `cicord.yaml` entry: its
plugins are part of source `cicord` (the name is reserved), merged with the bundled ones.
When a plugin is in both, the registry version is used only if its index `version` is a
valid semver **greater** than the bundled version; otherwise the bundled copy is used
(it ships with the binary). Installing a bundled plugin copies it to `plugins/<name>/`;
installing one from the official registry locks it in `cicord.lock` as `cicord/<name>`, like
any registry plugin, and `cicord plugin add cicord/<name>` works the same way. If the official
index cannot be read or verified, `cicord` still lists the bundled plugins and shows the
error. A build that embeds no official public key yet cannot verify the index: it does not
fetch it at all, and `cicord` lists the bundled plugins with an explanation (the Store
shows no signature badge; `cicord registry update` prints an informational line and does
not fail). The bundled copies remain in every build, for offline and first installs.

**Development.** A development build embeds a test key at build time
(`-ldflags "-X github.com/cicord/cicord/internal/registry.devOfficialKey=<base64>"`); only
such a build honours `CICORD_DEV_OFFICIAL_REGISTRY=<url>`, which points the official registry
at another URL (its index must be signed for that URL). Release builds ignore the variable:
nothing in the environment, `cicord.yaml` or the admin UI can change what is official.

### Setting up the official registry (project owner)

The content of `cicord/cicord-plugins` is generated from `examples/` by
`scripts/official-registry/prepare.sh <dir>` (the official plugins with standalone
`tsconfig.json`, their unit tests, the vendored `@cicord/sdk`, README, CONTRIBUTING, CI
workflows, and `index.yaml` written by `cicord plugin publish`, with local tags
`<name>/v<version>`). Signing keys and pushes are the owner's steps, in this order:

1. **Key pair**, offline, outside any repository:
   `cicord registry keygen --out ~/cicord-registry-signing.key`. Keep an offline backup of
   the private key file.
2. **Embed the public key** (the base64 line printed by `keygen`) in
   `internal/registry/sign.go` `OfficialKeys` and release Cicord; commit the same public key
   to `keys/official.pub` in cicord-plugins (its CI verifies with it). Done for the current
   production key, key ID `10d3620231e083f8`.
3. **Secret**: in cicord-plugins, create the `registry-signing` environment (deployments
   from `main` only) and store the content of the private key file as its
   `CICORD_REGISTRY_SIGNING_KEY` secret (the sign workflow reads it with
   `--key env:CICORD_REGISTRY_SIGNING_KEY`). Set the `CICORD_VERSION` Actions variable to a
   Cicord release tag: the CI builds that version of `cicord`, and the sign workflow refuses
   to run without it (the job holding the key never builds a moving branch). While
   cicord/cicord is private, also add a `CICORD_SOURCE_TOKEN` secret able to read it
   (pull requests from forks get no secret, so their checks need cicord/cicord public).
4. **Push** the prepared repository as is, branch and tags
   (`git push origin main && git push origin --tags`): the `commit:` fields of `index.yaml`
   pin those exact commits, so do not re-create the history from the files.
5. **First signature**: run the `sign` workflow (or locally
   `cicord registry sign . --key ~/cicord-registry-signing.key --registry-url https://github.com/cicord/cicord-plugins`
   and commit `index.yaml.sig`). Protect `main` (reviews required; allow the signing
   workflow's bot to push `index.yaml.sig`): the re-sign job signs whatever is on `main`,
   so branch protection is the real trust root.
