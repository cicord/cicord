A Cicord repository is plain YAML plus, optionally, the TypeScript sources of your own plugins.

<FileTree>

- cicord.yaml the Project: engine, source, registries, write-back, portal
- cicord.lock generated: pinned registry plugins (commit + content hash)
- servers/
  - my-community.yaml one Server per file, named after its key
  - assets/
    - my-community/ icons, banners, emojis, stickers, sounds (written by `cicord import`)
- bots/
  - moderator/
    - bot.yaml one Bot per directory: token reference, servers, plugin instances
- plugins/
  - welcome/ a local plugin: plugin.yaml, config.schema.json, src/
  - onboarding/
- portal/ optional: a custom community portal (`cicord portal init`)
- .github/
  - workflows/
    - cicord.yml CI: validate, plan on pull requests, wait for the sync
- .gitignore ignores `.cicord/` (the CLI's local state) and `*.db`
- README.md

</FileTree>

`cicord init` writes `cicord.yaml`, one server, one bot, the CI workflow, a `README.md` and a
`.gitignore`. The complete example repository
[`examples/basic`](https://github.com/cicord/cicord/tree/main/examples/basic) adds two
plugins, and [`examples/showcase`](https://github.com/cicord/cicord/tree/main/examples/showcase)
runs seven more.

:::tip[A real-world example]
The configuration of the official Cicord community server is public:
[github.com/cicord/cicord-community](https://github.com/cicord/cicord-community). It was
created by the setup wizard, commits `bots/**` and `plugins/**` directly and opens pull
requests for `servers/**`, and pins official registry plugins in `cicord.lock`.
:::

## Resources

Every file holds one resource, Kubernetes style:

```yaml
apiVersion: cicord.dev/v1alpha1 # the format version
kind: Server # Project, Server, Bot or Plugin
metadata:
  name: my-community # the key
spec:
  # …
```

| File                         | Kind        | Reference                                                          |
| ---------------------------- | ----------- | ------------------------------------------------------------------ |
| `cicord.yaml`                | `Project`   | [Project](../../configuration/project/)                            |
| `servers/<key>.yaml`         | `Server`    | [Server](../../configuration/server/)                              |
| `bots/<key>/bot.yaml`        | `Bot`       | [Bot](../../configuration/bot/)                                    |
| `plugins/<name>/plugin.yaml` | `Plugin`    | [Writing a plugin](../../plugins/writing/#the-manifest-pluginyaml) |
| `cicord.lock`                | (generated) | [Plugins overview](../../plugins/overview/#cicordlock)             |

`metadata.name` is the resource **key**. It must match the file name (`servers/<key>.yaml`)
or the directory name (`bots/<key>/`). `metadata` can also carry `labels` and
`annotations` (string maps).

The JSON Schemas in
[`spec/schemas/`](https://github.com/cicord/cicord/tree/main/spec/schemas)
(`project`, `server`, `bot` and `plugin.schema.json`) are normative, like the plugin SDK
types in `spec/sdk/cicord-sdk.d.ts`. They are published at
`https://cicord.dev/schemas/v1alpha1/<kind>.schema.json`: for completion and checks in your
editor, add `# yaml-language-server: $schema=https://cicord.dev/schemas/v1alpha1/server.schema.json`
(or a path to the schema) at the top of a file. See
[Editor support](../../getting-started/installation/#editor-support).

## Keys and display names

Keys match `^[a-z][a-z0-9-]{0,62}$` and **never change**. They are separate from the display
names shown in Discord:

```yaml
channels:
  general: # ← key: stable, used for references and state
    name: general-chat # ← display name: change it freely (a rename, not a recreate)
    category: community # ← a reference, by key
```

- References between resources always use keys: a channel's `category`, the role
  `hierarchy`, `access` roles, permission overwrite targets, a bot's `servers`, and plugin
  config fields marked `x-cicord-ref`.
- The runtime maps each key to a Discord ID in its database (the **resource map**), so a new
  display name is an update in Discord.
- Changing a key keeps the Discord resource as long as the display name and the kind stay
  the same: the old key is removed, the new one adopts the resource. `cicord mv` renames a key
  and every reference to it in one step. Changing the key **and** the display name in the
  same commit is a deletion plus a creation.

`cicord validate` checks every reference; a key that does not resolve fails validation.

## Configuration in git, data in the database

Only **configuration** goes to git. Everything that is **data** lives in the runtime's state
database (SQLite in the data directory, or PostgreSQL with `--database-url`):

| In git                                          | In the database                                            |
| ----------------------------------------------- | ---------------------------------------------------------- |
| Roles, channels, permissions, server settings   | The resource map (key → Discord ID, owner)                 |
| Bots, plugin instances, plugin settings         | Plugin storage (XP, warnings, tickets, member preferences) |
| Registries, write-back policies, portal options | Audit log, sessions, sync history                          |

This is why the state database must be [backed up](../../self-hosting/backups-and-secrets/),
and why state changes never cause commits.
