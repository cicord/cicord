A Cicord plugin is a small TypeScript (or JavaScript) module that runs **inside the runtime** and
reacts to Discord: gateway events, slash commands (with subcommands and autocomplete),
buttons and select menus, modals,
schedules, background tasks, events from other plugins and HTTP routes for the community
portal. There are no Node.js APIs: every side effect goes through the `ctx` object, and each
call is checked against the capabilities `bot.yaml` grants.

- [`cicord/cicord-plugins`](https://github.com/cicord/cicord-plugins) holds the sources of

  [`examples/showcase`](https://github.com/cicord/cicord/tree/main/examples/showcase) is a

## The loop

<Steps>

1. **Scaffold** the plugin:

   ```sh
   cicord plugin new plugins/hello          # --force overwrites existing files
   ```

   In a Cicord repository, it prints the instance to add to a bot, with the path from that
   bot's `bot.yaml`:

   ```yaml title="bots/bot/bot.yaml"
   spec:
     plugins:
       - name: hello
         source: ../../plugins/hello
         grants: [discord.messages.send]
   ```

2. **Run it** on the simulator. Every save hot-reloads the plugin:

   ```sh
   cicord dev --sim
   ```

   Open `http://127.0.0.1:7420/admin/`, sign in, and run `/hello` from the **Simulator**
   panel as the `owner` user (alice, bob and charlie must join the server first: the
   simulator refuses commands from non-members).

3. **Type the config** whenever `config.schema.json` changes:

   ```sh
   cicord plugin typegen plugins/hello
   ```

4. **Check it** like the runtime does, then smoke-test it on the simulator:

   ```sh
   cicord plugin build plugins/hello
   cicord plugin test plugins/hello
   ```

5. **Unit-test** it with `@cicord/sdk/testing` (see [Testing and limits](../testing/)):

   ```sh
   cd plugins/hello && npm install && npm test
   ```

</Steps>

## What `cicord plugin new` writes

<FileTree>

- plugins/hello/
  - plugin.yaml the manifest: static, reviewed in pull requests
  - config.schema.json JSON Schema of the instance config
  - tsconfig.json maps `@cicord/sdk` to .cicord/cicord-sdk.d.ts
  - .cicord/
    - cicord-sdk.d.ts the SDK types (`cicord plugin sdk-types` rewrites them)
  - src/
    - index.ts `export default definePlugin({...})`
    - cicord-env.d.ts typed `ctx.config`, generated by `cicord plugin typegen`
  - package.json unit tests only: `node --test`
  - test/
    - hello.test.ts an example unit test
  - vendor/
    - cicord-sdk-x.y.z.tgz `@cicord/sdk`, embedded in the cicord binary
  - .gitignore

</FileTree>

The runtime ignores `package.json`, `test/` and `vendor/`: it bundles `src/` itself. The
vendored tarball is the `@cicord/sdk` of your `cicord` version: commit `vendor/` and the unit
tests run anywhere, offline. `cicord plugin new --from-npm` (or `CICORD_FROM_NPM=true`)
depends on the [npm package](https://www.npmjs.com/package/@cicord/sdk) instead (`^<version>`);
to move an existing plugin over, replace the `"file:vendor/cicord-sdk-….tgz"` dependency of
its `package.json` with that range and delete `vendor/`. A `cicord` built without the portal
kit (`make build` without `make ui`) scaffolds the plugin without the test setup and says so.

`cicord plugin sdk-types <dir>` (re)writes `.cicord/cicord-sdk.d.ts`, for editors and `tsc`.

The scaffolded plugin is a single command:

```ts title="plugins/hello/src/index.ts"
import { command, definePlugin } from "@cicord/sdk";

export default definePlugin({
  commands: {
    hello: command({
      description: "Say hello",
      async run(ctx, interaction) {
        await interaction.reply(ctx.config.greeting);
      },
    }),
  },
});
```

## Enable it on a bot

A plugin runs once it is listed in a bot's `spec.plugins`, with every capability it requests
granted:

```yaml title="bots/moderator/bot.yaml"
spec:
  servers: [my-community]
  plugins:
    - name: welcome # instance key, unique within the bot
      source: ../../plugins/welcome # local path relative to bot.yaml (or <registry>/<plugin> + version)
      grants:
        [
          discord.messages.send,
          discord.channels.read,
          discord.members.read,
          discord.roles.assign,
          discord.dm.send,
          portal.links,
          storage.kv,
        ]
      config:
        channel: general
        autoRole: member
      overrides:
        my-community:
          config: # JSON merge patch (RFC 7386) over config
            message: "Hi {member}, welcome to {server}!"
```

One **instance** runs per (bot, plugin instance, server). The same plugin can run twice under
two instance names with different configs, and the instance's `servers:` limits it to some
of the bot's servers. Every field is described in
[Bot: plugin instances](../../configuration/bot/#plugin-instances).

## The manifest (`plugin.yaml`)

The manifest is **static and reviewable**. Everything dynamic (commands, handlers, routes)
comes from the code, and the builder checks that both agree. Schema:
[`spec/schemas/plugin.schema.json`](https://github.com/cicord/cicord/blob/main/spec/schemas/plugin.schema.json).

```yaml title="plugins/welcome/plugin.yaml"
# yaml-language-server: $schema=../../../../spec/schemas/plugin.schema.json
apiVersion: cicord.dev/v1alpha1
kind: Plugin
metadata:
  name: welcome # key: lowercase, digits, '-'
  version: 0.1.0 # semver
  displayName: Welcome # ≤ 64 characters
  description: Greets new members… # ≤ 280 characters
  license: Apache-2.0 # SPDX identifier
spec:
  engine: ">=0.2.0" # runtime versions this plugin supports
  entry: ./src/index.ts
  capabilities:
    [
      discord.messages.send,
      discord.channels.read,
      discord.members.read,
      discord.roles.assign,
      discord.dm.send,
      portal.links,
      storage.kv,
    ]
  intents: [ServerMembers]
  config:
    schema: ./config.schema.json
  # network:                       # required when http.fetch is requested
  #   allow: [api.example.com, "*.example.org"]
```

| Field                                                                                      | Description                                                                                                                                            |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `metadata.name`, `metadata.version`                                                        | **Required.** The plugin key and its semver version.                                                                                                   |
| `metadata.displayName`, `description`, `authors`, `license`, `homepage`, `keywords` (≤ 10) | Shown in the Store.                                                                                                                                    |
| `spec.engine`                                                                              | **Required.** Semver range of supported Cicord versions (`>=0.2.0` for the 0.2 SDK).                                                                   |
| `spec.entry`                                                                               | **Required.** Relative path of the module that default-exports `definePlugin(...)`.                                                                    |
| `spec.capabilities`                                                                        | What the plugin may do (below).                                                                                                                        |
| `spec.optional`                                                                            | Features that work without extra grants: `{ feature, capabilities?, intents?, when? }` ([below](#versioned-events-and-plugin-calls)).                  |
| `spec.intents`                                                                             | Gateway intents its event handlers need (below).                                                                                                       |
| `spec.delivery`, `spec.interop`                                                            | `at-least-once`, and the events, queries and actions it publishes, subscribes to, provides and consumes ([below](#versioned-events-and-plugin-calls)). |
| `spec.assets`                                                                              | Directory of read-only files packaged with the code, such as `./assets`.                                                                               |
| `spec.locales`                                                                             | Directory of translation catalogues, such as `./locales` ([Translation catalogues](../api/#translation-catalogues)).                                   |
| `spec.network.allow`, `spec.network.configurable`                                          | Hosts reachable with `http.fetch` (required with `http.fetch`); `configurable: true` lets an instance add hosts in `bot.yaml`.                         |
| `spec.secrets`                                                                             | Up to 32 credentials the instance binds in `bot.yaml`, with the hosts they may reach ([below](#sending-a-webhook-with-a-bound-credential)).            |
| `spec.privacy.records`                                                                     | The member data it keeps and its `erase`, `anonymize` or `retain` policy ([Member privacy](../api/#member-privacy)).                                   |
| `spec.config.schema`                                                                       | Relative path of the config JSON Schema.                                                                                                               |
| `spec.routes.types`                                                                        | Relative path of the [route contract](../api/#typed-routes) for typed portal clients.                                                                  |
| `spec.client.package`                                                                      | Optional npm package with React components for portals.                                                                                                |

## Capabilities and grants

Every capability in `spec.capabilities` must also be listed in the instance's `grants` in
`bot.yaml`. Otherwise `cicord validate` fails ("requests capabilities that are not granted"), so
a plugin update that asks for more shows up in review. At run time, a call that is not
granted throws a `CapabilityError` whose `capability` field names the missing one.

| Capability                                          | Allows                                                                                                                                                                            |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `discord.messages.read`                             | `channel.messages()`, `channel.message(id)`, `channel.pins()`, `message.reactionUsers()`, `message.pollVoters()`, `attachment.bytes()`                                            |
| `discord.messages.send`                             | `channel.send()`, `message.reply()`, `message.edit()` of the bot's own messages, `message.crosspost()`, `message.endPoll()`, `channel.typing()`                                   |
| `discord.messages.manage`                           | `message.delete()` (any message), `message.edit()` of other authors' messages, `pin()`, `unpin()`, `removeReaction()`; with `discord.messages.read`, `bulkDelete()` and `purge()` |
| `discord.webhooks.manage`                           | `channel.sendAs()`                                                                                                                                                                |
| `discord.reactions.manage`                          | `message.react()`                                                                                                                                                                 |
| `discord.members.read`                              | `ctx.server.member()`, `ctx.server.members()`, `role.members()` (with the `ServerMembers` intent), `ctx.server.voiceMembers()` (with `ServerVoiceStates`)                         |
| `discord.members.manage`                            | `member.setNickname()`                                                                                                                                                            |
| `discord.members.moderate`                          | `member.timeout()`, `removeTimeout()`, `kick()`, `ban()`, `ctx.server.ban()`, `unban()`, `bans()`                                                                                 |

| `discord.dm.send`                                   | `member.send()`, `ctx.server.sendDM()`, `retractDM()`                                                                                                                             |

Answering the plugin's own interactions (`reply`, `defer`, `followUp`, `update`,
`showModal`) needs no capability.

**Isolation.** Each instance only reaches its own server: channel IDs must belong to the
instance's server, or to a DM channel the instance opened or received. Storage and tasks belong to the installation. Event topics use bot scope by default and can declare server scope.

### Versioned events and plugin calls

Declare integrations in the manifest. Each file in `contracts/` follows the local contract name and version. An event schema describes its payload. A method file contains separate `input` and `output` schemas. Contracts support typed objects, arrays, primitives, enums, bounds and local references. The build checks literal topics and versions in publication calls, including the default version 1. Computed arguments are validated by the host on every publication. The host validates JSON in development and production. Run `cicord plugin typegen` to generate TypeScript declarations for installed contracts.

```yaml
spec:
  delivery: at-least-once
  capabilities: [storage.kv, events.publish]
  optional:
    - feature: pollRewards
      capabilities: [events.subscribe, plugins.query:polls.voters]
  interop:
    publishes: [{ topic: levelUp, version: 1, scope: server }]
    subscribes: [{ topic: polls.closed, version: 2 }]
    provides: { actions: [grantXp] }
    consumes: { queries: [polls.voters] }
```

`ctx.features.enabled("pollRewards")` checks the installation’s grants, optional intents and provider availability. Use `when: /cacheContent` on a feature to require a boolean switch in its effective configuration before requesting its optional intents. A plugin can report a configured feature with `ctx.features.report("pollRewards", false, reason)`. Another instance on the same server can discover a declared feature through `ctx.plugins.hasFeature(plugin, feature)`. Diagnostics shows feature status, provider choices, caller restrictions and missing grants. Granting a provider wildcard, for example `plugins.query:polls.*`, permits every declared query on that provider.

`ctx.events.publish("levelUp", payload, {version: 1, idempotencyKey})` records one delivery per subscribed installation. Derive the optional publication key from the originating operation to deduplicate repeated publications for 30 days. A subscriber gets `(ctx, payload, meta)`. Use `meta.id` to deduplicate the effect and commit that marker together with local state changes. The host orders deliveries per publisher and subscriber: the next event of a stream is delivered as soon as the previous one is acknowledged, so a stream drains at the speed of its handler. Failed deliveries are tried five times in all (backoff 1 s → 5 min) before parking them for 14 days. An event whose subscription a new revision no longer declares (topic, version or grant) is not a failure: it waits, and is parked after 24 hours. A server admin can replay or discard them in Diagnostics. The server owner and Discord administrators can inspect raw event data. The payload limit is 1 MiB. Publish compact summaries and provide a paginated query for longer lists. During an incompatible transition publish the old and new versions with separate calls. Legacy subscribers receive v1 on their own bot, at most once.

```ts
import { action, definePlugin, query } from "@cicord/sdk";

export default definePlugin({
  queries: {
    balance: query({
      async run(ctx, input: { userId: string }, call) {
        if (call.onBehalfOf?.userId !== input.userId) return null;
        return (await ctx.kv.get("balance:" + input.userId)) ?? 0;
      },
    }),
  },
  actions: {
    credit: action({
      async run(ctx, input: { userId: string; amount: number }) {
        return await ctx.kv.increment("balance:" + input.userId, input.amount);
      },
    }),
  },
});
```

Declare matching providers and schemas, e.g. `contracts/credit.v1.json`. Query contexts are read-only. Each method receives a host-authenticated caller and, for member-originated calls, a delegated principal. Private providers must check this member’s access to the requested record on every read. An optional installation-level `interop.allowCallers` list uses `bot/instance` identities. Consumers choose between duplicate providers using `interop.targets` on their own installation. Member routes and interactions in consumers, and provider method invocations, use isolated JS realms. Use durable storage for state shared between handlers.

:::caution[Provider calls do not see `onStart` state]
Each provider query or action runs in a fresh JS realm. The same applies to the member routes and interactions of a plugin that declares `interop.consumes`. Cicord evaluates the plugin's module again in that realm, but **`onStart` does not run there**. Module-level state filled by `onStart` or by other handlers, such as a `Map` cache or a catalog loaded from files, is empty. A lock built from a module-level promise chain does not serialise these calls against your events, tasks or cron jobs either. Read what the call needs from KV, files or assets inside the handler, and use KV atomics to serialise. A query context is read-only: KV writes, schedules, `ctx.status.set`, `ctx.features.report`, `ctx.http.fetch` and Discord effects throw `CapabilityError` with capability `read-only`. The realm keeps one request's caller, principal and write permission away from another request's continuations. Test the provider path with `callProvider` from `@cicord/sdk/testing` ([Testing](../testing/#provider-calls)).
:::

Call `ctx.plugins.query("economy", "balance", {userId})` or `ctx.plugins.call("economy", "credit", {userId, amount}, {idempotencyKey})`. Concurrent actions with the same key, input and principal share the recorded result for 30 days. The receipt belongs to the calling installation, so another caller using the same key runs its own action. A retry must carry the same input and be made on behalf of the same member (`onBehalfOf`: user id and resource scope): a result recorded on behalf of one member is never returned to a request made for another member or without one, and such a reuse fails with `invalid_input`. The member's access level is not part of the receipt: a retry after the member's access changed (for example a lost role) returns the action's original result, because its effect already happened. A call with a new key reaches the provider, which checks the caller's current access on every call. Provider KV writes, published events and the action receipt commit together. Verify external effects against Discord or the upstream service before repeating them after a lost response. Use the SDK testing helper `replayActionEffects` to inject interruptions after external effects. Only `PluginUnavailableError` means that no installation exists. After a refusal, report the configuration problem. After a timeout or handler error, retry the action with its original key. The host permits two call hops and rejects cycles.

### Attachments, assets and images

Send bytes with `files` on a message, DM, interaction reply, follow-up or component
update. Each file has a unique name, a `Uint8Array`, and optional `contentType` and
`description` fields. A message can include up to ten files. Each file must fit the
server's upload limit. For ordinary channel sends the bot needs Discord's
`AttachFiles` permission. On edit, omit `files` to preserve existing attachments.
Supply an array to replace them or an empty array to clear them.

:::caution[Experimental, opt-in]
Image rendering (`ctx.render.image`, the `render` capability) is experimental and opt-in in
0.2.0. It stays experimental until usage is confirmed with three target communities. Degrade
to a text message when the capability is not granted or a render fails.
:::

```ts
const card = await ctx.render.image({
  width: 640,
  height: 200,
  background: { gradient: ["#0d2540", "#386f87"] },
  layers: [
    { type: "text", x: 28, y: 42, text: "Welcome!", font: "Inter", size: 48, color: "#ffffff" },
    {
      type: "progress",
      x: 28,
      y: 150,
      width: 320,
      height: 12,
      value: 0.65,
      color: "#8df2c7",
      trackColor: "#21415f",
    },
  ],
});
await it.reply({
  embeds: [{ image: { url: "attachment://welcome.png" } }],
  files: [{ name: "welcome.png", ...card, description: "Community welcome card" }],
});
```

`ctx.assets.read("images/logo.png")` returns a fresh byte array relative to
`spec.assets`. The build snapshots regular files and includes their names and contents
in the same hashed bundle as the code. The directory can hold up to 5 MiB across
1,024 entries. Use slash-separated relative names. The loader rejects symlinks and
parent traversal. For UTF-8 text use `new TextEncoder().encode(text)` and
`new TextDecoder().decode(bytes)`. For a granted HTTP request, `(await
ctx.http.fetch(url)).bytes()` preserves the response bytes. A received Discord
attachment offers `await attachment.bytes()` for CDN downloads up to 8 MiB.

The Go renderer writes a PNG with sides of 1–2048 pixels, an area of at most 524,288
pixels (for example 1024×512, 724×724 or 2048×256), and up to 64 layers.
Backgrounds support colors, two-color vertical gradients, packaged assets and Discord
CDN URLs. Image layers take `source: { asset: "..." }` or `{ url: "..." }`, and
optional `circle` or `rounded` masks. Text uses Inter, Noto, emoji or a packaged
TrueType/OpenType font (`font: { asset: "fonts/title.ttf" }`). Its `x` aligns the
left, center or right edge and `y` sets the top. `maxWidth` truncates with an
ellipsis by default. Use `rect` for a solid block, `progress` for a fraction from
0 to 1 and `chart` with `kind: "bar" | "line"` and up to 256 numeric `values`.
Colors accept `#RRGGBB` and `#RRGGBBAA`. The distinct image sources of one render
(background and image layers, each decoded once) may total 524,288 decoded pixels.
Larger specs and sources are refused with a validation error.

The renderer is a confined WebAssembly worker with a hard 24 MiB memory ceiling and a
deadline of one second of wall-clock time. The deadline starts after its inputs are
downloaded and a worker slot is free. The runtime runs one worker per processor, at least
two and at most four. For reference, on an Apple M-series core a 700×220 welcome card with a
background and an avatar renders in about 115 ms. The largest envelope (a full canvas
and source, with 60 text layers in three fonts) takes about 600 ms. Slower hosts take
proportionally longer. All CDN inputs of one render share one download deadline.

`ctx.media.hash(attachmentOrURL, { algo })` returns a lowercase hexadecimal digest.
`sha256` identifies exact image bytes. `phash` and `dhash` produce 64-bit digests
for visual matching. `ctx.media.distance(a, b)` counts differing bits between two
equal-length digests. Downloads use the Discord CDN or the plugin's allowed hosts,
with egress checks at each redirect. Supported formats are PNG, JPEG, GIF (first
frame) and WebP. Input is limited to 8 MiB and four megapixels after decoding.
The host only reads the image header. `phash` and `dhash` decode the pixels in the same
confined worker as the renderer, with a 96 MiB memory ceiling and a 3-second deadline,
and at most half of the worker slots go to hashing. A crafted image that would take
minutes to decode fails with an error instead of holding the runtime. `sha256` hashes the
bytes of any image with a valid header.

For unit tests, `createTestContext` accepts `assets`, a binary response from its
`fetch` fixture, and optional `renderImage` and `hashImage` functions. Use
`harness.attachment(file)` for command inputs. Simulator runs use the packaged Go
renderer and image hasher (the same confined worker) and a local Discord CDN.

### Network egress

`spec.network.allow` takes public DNS host names with an optional port. `*.example.com`
matches subdomains, not `example.com` itself. IP literals, `localhost`, single-label names,
reserved suffixes (`.local`, `.internal`, `.arpa`…) and wildcards on a bare TLD are
rejected. On every request the runtime also checks that every resolved address is public,
connects to the address it checked (no DNS rebinding), re-checks every redirect hop (at
most 5), allows only `https` and refuses credentials in URLs. After DNS resolution it refuses
loopback, private (RFC 1918, `fc00::/7`), link-local (including the `169.254.169.254`
metadata address), CGNAT, multicast, unspecified and IPv4-mapped addresses. `cicord dev` relaxes the address checks and allows plain
`http`, so a plugin can call a local service during development; `cicord serve` never does.

### Sending a webhook with a bound credential

Declare the logical webhook name, its allowed provider hosts and the send operation in the manifest.

```yaml
secrets:
  - name: STAFF_WEBHOOK
    use: webhook.send
    hosts: [discord.com, hooks.slack.com]
```

Bind that name in `bot.yaml` and keep the incoming webhook URL in the operator secret store:

```yaml
plugins:
  - name: guard
    source: cicord/guard
    secrets:
      STAFF_WEBHOOK: { secretRef: CICORD_STAFF_WEBHOOK }
```

A plugin `secretRef` must start with `CICORD_`. The runtime resolves it from the environment, then the encrypted store, so the namespace keeps other process credentials (`AWS_SECRET_ACCESS_KEY`, `PGPASSWORD`…) out of reach of a `bot.yaml` line. The runtime's own credentials (`CICORD_SECRET_KEY`, `CICORD_DATABASE_URL`, registry tokens, bot tokens…) stay reserved and cannot be bound either. `cicord validate` refuses any other name. For Discord, send a message with `ctx.http.fetch(ctx.secrets.ref("STAFF_WEBHOOK"), {method: "POST", json: {content: message}})`. Slack incoming webhooks use `{text: message}`. The host accepts the provider's exact incoming-webhook endpoint and returns the HTTP status. A reply carries empty headers and body. Credential declarations for API keys and captcha fields continue to use their approved header, form or JSON positions.

## Intents

Event handlers need gateway intents, which the manifest must declare. A handler without its
intent is a build error.

| Handler                                           | Intent                                                                        |
| ------------------------------------------------- | ----------------------------------------------------------------------------- |
| `memberJoin`, `memberLeave`, `memberUpdate`       | `ServerMembers` (privileged)                                                  |
| `messageCreate`, `messageUpdate`, `messageDelete` | `ServerMessages`; add `MessageContent` (privileged) to read `message.content` |
| `reactionAdd`, `reactionRemove`                   | `ServerMessageReactions`                                                      |
| `voiceStateUpdate`                                | `ServerVoiceStates`                                                           |

Two calls need an intent too, checked when they are called: `role.members()` needs
`ServerMembers` (see [Members of a role](../api/#members-of-a-role)) and
`ctx.server.voiceMembers()` needs `ServerVoiceStates` (see [Voice](../api/#voice)).

**Message content is gated per plugin.** A plugin that does not declare `MessageContent`
gets an empty `message.content`, `attachments` and `embeds`, in events and in
`channel.messages()`, even when another plugin of the bot declares it, unless the message is
the bot's own, mentions the bot or is a DM. Declare it only when the plugin reads what people
write (the official `levels` plugin does, to ignore very short messages); a plugin that only
needs who posted and when (flood protection, ticket activity) does not.

A bot connects with the union of its plugins' intents, plus the bot's own `spec.intents` and
what the reconciler needs. Privileged intents must also be enabled in the Discord developer
portal: when one is missing, the runtime does not open the gateway and the bot status names
the toggle to turn on. See [Bot: gateway intents](../../configuration/bot/#gateway-intents).

## Configuration schema

`config.schema.json` is JSON Schema 2020-12. The runtime checks each instance's config against
it, per server, after merging `overrides.<server>.config`. Schema `default`s are applied
before the plugin sees `ctx.config`: at the top level, in nested objects, in every object
element of arrays (`steps[].multiple`) and through local `$ref`s (not inside
`additionalProperties` maps nor `oneOf`/`anyOf` alternatives). An absent optional object is
created only when its defaults cover all its `required` fields, so an optional
`webhook: { url, format }` with a required `url` stays absent. Cicord adds three keywords:

| Keyword           | Values                                      | Effect                                                                                                                                                                     |
| ----------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `x-cicord-ref`    | `channel`, `category`, `role`               | The value is a resource key of the server (a string, or an array of strings). The admin console renders a picker; `cicord validate` checks the key exists on every server. |
| `x-cicord-widget` | `textarea`, `markdown`, `color`, `duration` | Rendering hint for the admin console form.                                                                                                                                 |
| `x-cicord-access` | `admin` (default), `moderator`              | Who may edit the top-level field in the admin console. Edits are written back to `bot.yaml` as a commit or a pull request.                                                 |

```json title="plugins/welcome/config.schema.json"
{
  "type": "object",
  "required": ["channel"],
  "properties": {
    "channel": { "type": "string", "x-cicord-ref": "channel" },
    "message": {
      "type": "string",
      "default": "Welcome {member} to {server}!",
      "x-cicord-widget": "textarea",
      "x-cicord-access": "moderator"
    },
    "autoRole": { "type": "string", "x-cicord-ref": "role" },
    "dmOnboarding": { "type": "boolean", "default": true }
  },
  "additionalProperties": false
}
```

`cicord plugin typegen` turns the schema into a module augmentation, so `ctx.config` is typed.
A field that is required, or has a default the runtime applies, is non-optional:

```ts title="src/cicord-env.d.ts (generated, do not edit)"
declare module "@cicord/sdk" {
  interface PluginConfig {
    channel: string;
    message: string;
    autoRole?: string;
    dmOnboarding: boolean;
  }
}
export {};
```

Array items follow the same rule: with `"multiple": { "type": "boolean", "default": false }`
in `steps.items`, `ctx.config.steps[0].multiple` is a `boolean`, never `undefined`. Run
`cicord plugin typegen --check` in CI to catch a stale file.

## Build model

The runtime bundles plugins itself, with esbuild used as a Go library (no Node.js):

- The entry is `spec.entry`, which must `export default definePlugin({...})`.
- Every imported module is bundled in. Pure-JS npm libraries work; Node.js built-ins
  (`fs`, `path`, `node:*`…) are refused at build time.
- `@cicord/sdk` is the only module resolved at run time (the host provides it).
- Target ES2023 syntax (QuickJS-ng supports all of it, async generators included), with an
  inline source map, so stack traces point at `src/index.ts:12:5`.
- At load time the definition is checked against the manifest: a handler without its intent,
  `schedules`/`tasks` without `scheduler`, `routes` without `portal.routes`,
  `subscriptions` without `events.subscribe`, an unknown key in `definePlugin()`, an invalid
  command, cron expression or route `access` all reject the revision, and the previous one
  keeps running.

`cicord plugin build <dir>` does exactly this and prints the definition (commands, events,
routes); `--out` also writes the bundle, `-o json` prints JSON.

### Package boundary

Cicord compiles each plugin with a read-only view of its package. Relative modules, local TypeScript aliases and dependencies shipped within the package resolve inside that view. `@cicord/sdk` is provided by the host. Ancestor workspaces, external symlinks and host files are unavailable to imports, TypeScript configuration, source maps and glob resolution. Keep plugin config schema references within the schema document, using `$defs` for shared definitions.

## Type checking

Type-check with the scaffolded `tsconfig.json`, which maps `@cicord/sdk` to
`.cicord/cicord-sdk.d.ts` (the examples of the Cicord repository map it to
`spec/sdk/cicord-sdk.d.ts`) and uses `"lib": ["ES2023"]` (the engine provides the ES2023
built-ins, such as `toSorted` and `findLast`) and `"types": []` so no DOM or Node types leak
in:

```sh
tsc --noEmit -p plugins/hello
```

The normative SDK contract is
[`spec/sdk/cicord-sdk.d.ts`](https://github.com/cicord/cicord/blob/main/spec/sdk/cicord-sdk.d.ts);
`cicord plugin sdk-types <dir>` rewrites the local copy.

## Disabling an installation

Set `enabled: false` in the installation's `config` in `bot.yaml`, or change the **Enabled** switch in its admin settings. The switch may also be set in a server override. An inactive installation may use just `config: {enabled: false}`, including when the plugin's active config schema requires fields. This switch belongs to the host. Existing manifests and schemas can use it without a code change.

The instance stays listed as **Disabled**. Its commands, routes, subscriptions and schedules are unavailable. Disabling stops its VM without invoking a shutdown hook. Already completed external effects and stored plugin data persist. Queued deliveries retain their payloads, attempts and deadlines while the installation is disabled. Re-enabling validates the full config, bindings and grants, then starts the installation normally. Overdue work resumes under the plugin's declared retry policy. Privacy erasures requested while the installation was disabled are applied before startup.

To verify inactive behavior, save `enabled: false` in a YAML file and pass it to `cicord plugin test <directory> --config <file>`. The simulator checks that the disabled installation registered no executable handlers.
