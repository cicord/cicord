A Cicord plugin is a small TypeScript (or JavaScript) module that runs **inside the runtime** and
reacts to Discord: gateway events, slash commands (with subcommands and autocomplete),
buttons and select menus, modals,
schedules, background tasks, events from other plugins and HTTP routes for the community
portal. There are no Node.js APIs: every side effect goes through the `ctx` object, and each
call is checked against the capabilities `bot.yaml` grants.

## References and examples

- [`spec/sdk/cicord-sdk.d.ts`](https://github.com/cicord/cicord/blob/main/spec/sdk/cicord-sdk.d.ts)
  is the `@cicord/sdk` API; the published `@cicord/sdk` package ships the same types.
- Plugin instances are described in [Bot: plugin instances](../../configuration/bot/#plugin-instances),
  the manifest and capabilities [below](#the-manifest-pluginyaml), and the SDK semantics in the
  [plugin API](../api/).
- [`spec/schemas/plugin.schema.json`](https://github.com/cicord/cicord/blob/main/spec/schemas/plugin.schema.json)
  is the `plugin.yaml` schema.
- [`cicord/cicord-plugins`](https://github.com/cicord/cicord-plugins) holds the sources of
  the ten [official plugins](../official/), each with its unit tests.
- [`examples/basic/plugins`](https://github.com/cicord/cicord/tree/main/examples/basic/plugins)
  holds `welcome` and `onboarding`, and
  [`examples/showcase`](https://github.com/cicord/cicord/tree/main/examples/showcase) is a
  complete repository whose seven plugins together use the whole SDK:

  | Plugin           | What it shows                                                                                                     |
  | ---------------- | ----------------------------------------------------------------------------------------------------------------- |
  | `tickets`        | Buttons, modals, plugin-owned private channels                                                                    |
  | `polls`          | Select menus, buttons with data in their ids, live updates, tasks, subcommands, autocomplete, cross-plugin events |
  | `levels`         | Message content, reactions, role rewards, cron, a public portal route                                             |
  | `moderation`     | Permission checks, DMs, timeouts, kicks and bans, expiring KV, `http.fetch`                                       |
  | `reaction-roles` | Role panels with buttons, a select menu or reactions, edited in place                                             |
  | `audit-log`      | Member and message events, subscriptions, batched posts                                                           |
  | `announcements`  | Time-zone schedules evaluated by a minute tick, `/announce` with a modal and tasks                                |

  They are the copies of the official plugins bundled with the binary;
  [SDK coverage](../coverage/) maps every SDK feature to the plugin and the end-to-end test
  that exercise it.

## The loop

<Steps>

1. **Scaffold** the plugin:

   ```sh
   cicord plugin new plugins/hello          # --force overwrites existing files
   ```

   In a Cicord repository, it prints the instance to add to a bot, with the path from that
   bot's `bot.yaml`:

   ```yaml title="bots/bot/bot.yaml"
   spec:
     plugins:
       - name: hello
         source: ../../plugins/hello
         grants: [discord.messages.send]
   ```

2. **Run it** on the simulator. Every save hot-reloads the plugin:

   ```sh
   cicord dev --sim
   ```

   Open `http://127.0.0.1:7420/admin/`, sign in, and run `/hello` from the **Simulator**
   panel as the `owner` user (alice, bob and charlie must join the server first: the
   simulator refuses commands from non-members).

3. **Type the config** whenever `config.schema.json` changes:

   ```sh
   cicord plugin typegen plugins/hello
   ```

4. **Check it** like the runtime does, then smoke-test it on the simulator:

   ```sh
   cicord plugin build plugins/hello
   cicord plugin test plugins/hello
   ```

5. **Unit-test** it with `@cicord/sdk/testing` (see [Testing and limits](../testing/)):

   ```sh
   cd plugins/hello && npm install && npm test
   ```

</Steps>

## What `cicord plugin new` writes

<FileTree>

- plugins/hello/
  - plugin.yaml the manifest: static, reviewed in pull requests
  - config.schema.json JSON Schema of the instance config
  - tsconfig.json maps `@cicord/sdk` to .cicord/cicord-sdk.d.ts
  - .cicord/
    - cicord-sdk.d.ts the SDK types (`cicord plugin sdk-types` rewrites them)
  - src/
    - index.ts `export default definePlugin({...})`
    - cicord-env.d.ts typed `ctx.config`, generated by `cicord plugin typegen`
  - package.json unit tests only: `node --test`
  - test/
    - hello.test.ts an example unit test
  - vendor/
    - cicord-sdk-x.y.z.tgz `@cicord/sdk`, embedded in the cicord binary
  - .gitignore

</FileTree>

The runtime ignores `package.json`, `test/` and `vendor/`: it bundles `src/` itself. The
vendored tarball is the `@cicord/sdk` of your `cicord` version: commit `vendor/` and the unit
tests run anywhere, offline. `cicord plugin new --from-npm` (or `CICORD_FROM_NPM=true`)
depends on the [npm package](https://www.npmjs.com/package/@cicord/sdk) instead (`^<version>`);
to move an existing plugin over, replace the `"file:vendor/cicord-sdk-….tgz"` dependency of
its `package.json` with that range and delete `vendor/`. A `cicord` built without the portal
kit (`make build` without `make ui`) scaffolds the plugin without the test setup and says so.

`cicord plugin sdk-types <dir>` (re)writes `.cicord/cicord-sdk.d.ts`, for editors and `tsc`.

The scaffolded plugin is a single command:

```ts title="plugins/hello/src/index.ts"
import { command, definePlugin } from "@cicord/sdk";

export default definePlugin({
  commands: {
    hello: command({
      description: "Say hello",
      async run(ctx, interaction) {
        await interaction.reply(ctx.config.greeting);
      },
    }),
  },
});
```

## Enable it on a bot

A plugin runs once it is listed in a bot's `spec.plugins`, with every capability it requests
granted:

```yaml title="bots/moderator/bot.yaml"
spec:
  servers: [my-community]
  plugins:
    - name: welcome # instance key, unique within the bot
      source: ../../plugins/welcome # local path relative to bot.yaml (or <registry>/<plugin> + version)
      grants:
        [
          discord.messages.send,
          discord.channels.read,
          discord.members.read,
          discord.roles.assign,
          discord.dm.send,
          portal.links,
          storage.kv,
        ]
      config:
        channel: general
        autoRole: member
      overrides:
        my-community:
          config: # JSON merge patch (RFC 7386) over config
            message: "Hi {member}, welcome to {server}!"
```

One **instance** runs per (bot, plugin instance, server). The same plugin can run twice under
two instance names with different configs, and the instance's `servers:` limits it to some
of the bot's servers. Every field is described in
[Bot: plugin instances](../../configuration/bot/#plugin-instances).

## The manifest (`plugin.yaml`)

The manifest is **static and reviewable**. Everything dynamic (commands, handlers, routes)
comes from the code, and the builder checks that both agree. Schema:
[`spec/schemas/plugin.schema.json`](https://github.com/cicord/cicord/blob/main/spec/schemas/plugin.schema.json).

```yaml title="plugins/welcome/plugin.yaml"
# yaml-language-server: $schema=../../../../spec/schemas/plugin.schema.json
apiVersion: cicord.dev/v1alpha1
kind: Plugin
metadata:
  name: welcome # key: lowercase, digits, '-'
  version: 0.1.0 # semver
  displayName: Welcome # ≤ 64 characters
  description: Greets new members… # ≤ 280 characters
  license: Apache-2.0 # SPDX identifier
spec:
  engine: ">=0.1.0" # runtime versions this plugin supports
  entry: ./src/index.ts
  capabilities:
    [
      discord.messages.send,
      discord.channels.read,
      discord.members.read,
      discord.roles.assign,
      discord.dm.send,
      portal.links,
      storage.kv,
    ]
  intents: [ServerMembers]
  config:
    schema: ./config.schema.json
  # network:                       # required when http.fetch is requested
  #   allow: [api.example.com, "*.example.org"]
```

| Field                                                                                      | Description                                                                           |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| `metadata.name`, `metadata.version`                                                        | **Required.** The plugin key and its semver version.                                  |
| `metadata.displayName`, `description`, `authors`, `license`, `homepage`, `keywords` (≤ 10) | Shown in the Store.                                                                   |
| `spec.engine`                                                                              | **Required.** Semver range of supported Cicord versions.                              |
| `spec.entry`                                                                               | **Required.** Relative path of the module that default-exports `definePlugin(...)`.   |
| `spec.capabilities`                                                                        | What the plugin may do (below).                                                       |
| `spec.assets` | Directory of read-only files to include in the plugin bundle, such as `./assets`. |
| `spec.intents`                                                                             | Gateway intents its event handlers need (below).                                      |
| `spec.network.allow`                                                                       | Hosts reachable with `http.fetch`. Required when `http.fetch` is requested.           |
| `spec.config.schema`                                                                       | Relative path of the config JSON Schema.                                              |
| `spec.routes.types`                                                                        | Relative path of the [route contract](../api/#typed-routes) for typed portal clients. |
| `spec.client.package`                                                                      | Optional npm package with React components for portals.                               |

## Capabilities and grants

Every capability in `spec.capabilities` must also be listed in the instance's `grants` in
`bot.yaml`. Otherwise `cicord validate` fails ("requests capabilities that are not granted"), so
a plugin update that asks for more shows up in review. At run time, a call that is not
granted throws a `CapabilityError` whose `capability` field names the missing one.

| Capability                            | Allows                                                                                                                            |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `discord.messages.read`               | `channel.messages()` (history), `channel.message(id)`, `attachment.bytes()` |
| `discord.messages.send`               | `channel.send()`, `message.reply()`, `message.edit()` of the bot's own messages                                                   |
| `discord.messages.manage`             | `message.delete()` (any message), `message.edit()` of other authors' messages                                                     |
| `discord.reactions.manage`            | `message.react()`                                                                                                                 |
| `discord.members.read`                | `ctx.server.member()`, `role.members()` (with the `ServerMembers` intent), `ctx.server.voiceMembers()` (with `ServerVoiceStates`) |
| `discord.members.manage`              | `member.setNickname()`                                                                                                            |
| `discord.members.moderate`            | `member.timeout()`, `kick()`, `ban()`                                                                                             |
| `discord.roles.assign`                | `member.addRole()`, `removeRole()`                                                                                                |
| `discord.channels.read`               | `ctx.server.channel()`                                                                                                            |
| `discord.channels.manage`             | `ctx.server.createChannel()` / `editChannel()` / `deleteChannel()` (plugin-owned channels)                                        |
| `discord.threads.manage`              | `channel.createThread()`                                                                                                          |
| `discord.voice.move`                  | `member.moveTo()` (to a voice channel), `member.disconnect()` (from voice)                                                        |
| `discord.dm.send`                     | `member.send()`                                                                                                                   |
| `storage.kv`                          | `ctx.kv`                                                                                                                          |
| `scheduler`                           | `schedules`, `tasks`, `ctx.schedule`                                                                                              |
| `http.fetch`                          | `ctx.http.fetch()` to the `spec.network.allow` hosts                                                                              |
| `render` | `ctx.render.image()` |
| `media.analyze` | `ctx.media.hash()`, `ctx.media.distance()` |
| `portal.routes`                       | `routes`                                                                                                                          |
| `portal.links`                        | `ctx.portal.link()`                                                                                                               |
| `events.publish` / `events.subscribe` | `ctx.events.publish()` / `subscriptions`                                                                                          |

Answering the plugin's own interactions (`reply`, `defer`, `followUp`, `update`,
`showModal`) needs no capability.

**Isolation.** Each instance only reaches its own server: channel IDs must belong to the
instance's server, or to a DM channel the instance opened or received. Storage, tasks and
events are scoped to the instance or to its (bot, server).

### Attachments, assets and images

Send bytes with `files` on a message, DM, interaction reply, follow-up or component
update. Each file has a unique name, a `Uint8Array`, and optional `contentType` and
`description` fields. A message can include up to ten files. Each file must fit the
server's upload limit. For ordinary channel sends the bot needs Discord's
`AttachFiles` permission. On edit, omit `files` to preserve existing attachments.
Supply an array to replace them or an empty array to clear them.

```ts
const card = await ctx.render.image({
  width: 640,
  height: 200,
  background: { gradient: ["#0d2540", "#386f87"] },
  layers: [
    { type: "text", x: 28, y: 42, text: "Welcome!", font: "Inter", size: 48, color: "#ffffff" },
    { type: "progress", x: 28, y: 150, width: 320, height: 12, value: 0.65,
      color: "#8df2c7", trackColor: "#21415f" },
  ],
});
await it.reply({
  embeds: [{ image: { url: "attachment://welcome.png" } }],
  files: [{ name: "welcome.png", ...card, description: "Community welcome card" }],
});
```

`ctx.assets.read("images/logo.png")` returns a fresh byte array relative to
`spec.assets`. The build snapshots regular files and includes their names and contents
in the same hashed bundle as the code. The directory can hold up to 5 MiB across
1,024 entries. Use slash-separated relative names. The loader rejects symlinks and
parent traversal. For UTF-8 text use `new TextEncoder().encode(text)` and
`new TextDecoder().decode(bytes)`. For a granted HTTP request, `(await
ctx.http.fetch(url)).bytes()` preserves the response bytes. A received Discord
attachment offers `await attachment.bytes()` for CDN downloads up to 8 MiB.

The Go renderer writes a PNG from dimensions of 1–2048 pixels and up to 64 layers.
Backgrounds support colors, two-color vertical gradients, packaged assets and Discord
CDN URLs. Image layers take `source: { asset: "..." }` or `{ url: "..." }`, and
optional `circle` or `rounded` masks. Text uses Inter, Noto, emoji or a packaged
TrueType/OpenType font (`font: { asset: "fonts/title.ttf" }`). Its `x` aligns the
left, center or right edge and `y` sets the top. `maxWidth` truncates with an
ellipsis by default. Use `rect` for a solid block, `progress` for a fraction from
0 to 1 and `chart` with `kind: "bar" | "line"` and up to 256 numeric `values`.
Colors accept `#RRGGBB` and `#RRGGBBAA`. The renderer runs with a hard 16 MiB
linear-memory ceiling and a 300 ms execution deadline after its inputs arrive.
Complex inputs can exhaust either budget within the maximum dimensions.

`ctx.media.hash(attachmentOrURL, { algo })` returns a lowercase hexadecimal digest.
`sha256` identifies exact image bytes. `phash` and `dhash` produce 64-bit digests
for visual matching. `ctx.media.distance(a, b)` counts differing bits between two
equal-length digests. Downloads use the Discord CDN or the plugin's allowed hosts,
with egress checks at each redirect. Supported formats are PNG, JPEG, GIF (first
frame) and WebP. Input is limited to 8 MiB and four megapixels after decoding.

For unit tests, `createTestContext` accepts `assets`, a binary response from its
`fetch` fixture, and optional `renderImage` and `hashImage` functions. Use
`harness.attachment(file)` for command inputs. Simulator runs use the packaged Go
renderer, native image hashes and a local Discord CDN.

### Network egress

`spec.network.allow` takes public DNS host names with an optional port. `*.example.com`
matches subdomains, not `example.com` itself. IP literals, `localhost`, single-label names,
reserved suffixes (`.local`, `.internal`, `.arpa`…) and wildcards on a bare TLD are
rejected. On every request the runtime also checks that every resolved address is public,
connects to the address it checked (no DNS rebinding), re-checks every redirect hop (at
most 5), allows only `https` and refuses credentials in URLs. After DNS resolution it refuses
loopback, private (RFC 1918, `fc00::/7`), link-local (including the `169.254.169.254`
metadata address), CGNAT, multicast, unspecified and IPv4-mapped addresses. `cicord dev` relaxes the address checks and allows plain
`http`, so a plugin can call a local service during development; `cicord serve` never does.

## Intents

Event handlers need gateway intents, which the manifest must declare. A handler without its
intent is a build error.

| Handler                                           | Intent                                                                        |
| ------------------------------------------------- | ----------------------------------------------------------------------------- |
| `memberJoin`, `memberLeave`, `memberUpdate`       | `ServerMembers` (privileged)                                                  |
| `messageCreate`, `messageUpdate`, `messageDelete` | `ServerMessages`; add `MessageContent` (privileged) to read `message.content` |
| `reactionAdd`, `reactionRemove`                   | `ServerMessageReactions`                                                      |
| `voiceStateUpdate`                                | `ServerVoiceStates`                                                           |

Two calls need an intent too, checked when they are called: `role.members()` needs
`ServerMembers` (see [Members of a role](../api/#members-of-a-role)) and
`ctx.server.voiceMembers()` needs `ServerVoiceStates` (see [Voice](../api/#voice)).

**Message content is gated per plugin.** A plugin that does not declare `MessageContent`
gets an empty `message.content`, `attachments` and `embeds`, in events and in
`channel.messages()`, even when another plugin of the bot declares it, unless the message is
the bot's own, mentions the bot or is a DM. Declare it only when the plugin reads what people
write (the official `levels` plugin does, to ignore very short messages); a plugin that only
needs who posted and when (flood protection, ticket activity) does not.

A bot connects with the union of its plugins' intents, plus the bot's own `spec.intents` and
what the reconciler needs. Privileged intents must also be enabled in the Discord developer
portal: when one is missing, the runtime does not open the gateway and the bot status names
the toggle to turn on. See [Bot: gateway intents](../../configuration/bot/#gateway-intents).

## Configuration schema

`config.schema.json` is JSON Schema 2020-12. The runtime checks each instance's config against
it, per server, after merging `overrides.<server>.config`. Schema `default`s are applied
before the plugin sees `ctx.config`: at the top level, in nested objects, in every object
element of arrays (`steps[].multiple`) and through local `$ref`s (not inside
`additionalProperties` maps nor `oneOf`/`anyOf` alternatives). An absent optional object is
created only when its defaults cover all its `required` fields, so an optional
`webhook: { url, format }` with a required `url` stays absent. Cicord adds three keywords:

| Keyword           | Values                                      | Effect                                                                                                                                                                     |
| ----------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `x-cicord-ref`    | `channel`, `category`, `role`               | The value is a resource key of the server (a string, or an array of strings). The admin console renders a picker; `cicord validate` checks the key exists on every server. |
| `x-cicord-widget` | `textarea`, `markdown`, `color`, `duration` | Rendering hint for the admin console form.                                                                                                                                 |
| `x-cicord-access` | `admin` (default), `moderator`              | Who may edit the top-level field in the admin console. Edits are written back to `bot.yaml` as a commit or a pull request.                                                 |

```json title="plugins/welcome/config.schema.json"
{
  "type": "object",
  "required": ["channel"],
  "properties": {
    "channel": { "type": "string", "x-cicord-ref": "channel" },
    "message": {
      "type": "string",
      "default": "Welcome {member} to {server}!",
      "x-cicord-widget": "textarea",
      "x-cicord-access": "moderator"
    },
    "autoRole": { "type": "string", "x-cicord-ref": "role" },
    "dmOnboarding": { "type": "boolean", "default": true }
  },
  "additionalProperties": false
}
```

`cicord plugin typegen` turns the schema into a module augmentation, so `ctx.config` is typed.
A field that is required, or has a default the runtime applies, is non-optional:

```ts title="src/cicord-env.d.ts (generated, do not edit)"
declare module "@cicord/sdk" {
  interface PluginConfig {
    channel: string;
    message: string;
    autoRole?: string;
    dmOnboarding: boolean;
  }
}
export {};
```

Array items follow the same rule: with `"multiple": { "type": "boolean", "default": false }`
in `steps.items`, `ctx.config.steps[0].multiple` is a `boolean`, never `undefined`. Run
`cicord plugin typegen --check` in CI to catch a stale file.

## Build model

The runtime bundles plugins itself, with esbuild used as a Go library (no Node.js):

- The entry is `spec.entry`, which must `export default definePlugin({...})`.
- Every imported module is bundled in. Pure-JS npm libraries work; Node.js built-ins
  (`fs`, `path`, `node:*`…) are refused at build time.
- `@cicord/sdk` is the only module resolved at run time (the host provides it).
- Target ES2023 syntax (QuickJS-ng supports all of it, async generators included), with an
  inline source map, so stack traces point at `src/index.ts:12:5`.
- At load time the definition is checked against the manifest: a handler without its intent,
  `schedules`/`tasks` without `scheduler`, `routes` without `portal.routes`,
  `subscriptions` without `events.subscribe`, an unknown key in `definePlugin()`, an invalid
  command, cron expression or route `access` all reject the revision, and the previous one
  keeps running.

`cicord plugin build <dir>` does exactly this and prints the definition (commands, events,
routes); `--out` also writes the bundle, `-o json` prints JSON.

## Type checking

Type-check with the scaffolded `tsconfig.json`, which maps `@cicord/sdk` to
`.cicord/cicord-sdk.d.ts` (the examples of the Cicord repository map it to
`spec/sdk/cicord-sdk.d.ts`) and uses `"lib": ["ES2023"]` (the engine provides the ES2023
built-ins, such as `toSorted` and `findLast`) and `"types": []` so no DOM or Node types leak
in:

```sh
tsc --noEmit -p plugins/hello
```

The normative SDK contract is
[`spec/sdk/cicord-sdk.d.ts`](https://github.com/cicord/cicord/blob/main/spec/sdk/cicord-sdk.d.ts);
`cicord plugin sdk-types <dir>` rewrites the local copy.
