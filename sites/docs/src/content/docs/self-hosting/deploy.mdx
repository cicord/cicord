`cicord serve` is a single static binary: the runtime (reconciler, bot gateways, plugin host),
the HTTP API, the admin console (`/admin/`) and the default community portal (`/`). It needs a
data directory and outbound access to Discord (and to your git host). There is no database
server, no Node.js and no `git` binary to install: git is implemented in Go and SQLite is a
pure Go driver. If you prefer, a [PostgreSQL database](#state-store-sqlite-or-postgresql)
can hold the runtime state instead of SQLite.

:::tip[Step by step]
[Production on a VPS](../production-vps/) applies this page to one Ubuntu server: Docker,
Caddy for the public portal, the admin console on a Tailscale tailnet, a GitHub App, backups
and automatic updates. This page is the reference for each option.
:::

:::danger[Never deploy `cicord dev`]
`cicord dev` is for local development only: it edits the working tree, and with `--sim` (or the
runtime token) `/auth/dev-login` signs in as any user. Always run `cicord serve` on a server.
:::

## `cicord serve`

```text
cicord serve [dir] [--data-dir DIR] [--database-url URL] [--listen ADDR] [--public-url URL] [--admin-url URL]
             [--cors-origin ORIGIN]... [--metrics-listen ADDR] [--log-level LEVEL] [--local] [--github-app-key-file FILE]
```

- **`dir`** (default `.`) must contain `cicord.yaml`. Its `spec.source` says what to follow:
  - `provider: github` or `git`, with `repo`, `branch` (default `main`), `path` and
    `pollInterval` (default `1m`): the runtime clones and polls the repository. `dir` only
    needs `cicord.yaml`.
  - `provider: embedded`: on first start, the contents of `dir` are imported into a bare
    repository in the data directory (`repo.git`), which is then the source of truth.
  - no `spec.source`, or **`--local`**: `dir` is watched as is (no git). Admin console edits
    are written to the files, so `dir` must be writable.
- **`--listen`** defaults to `:7420`.
- **`--public-url`** (env `CICORD_PUBLIC_URL`) is the URL browsers use, for example
  `https://cicord.example.org`. **Set it for every non-local deployment**: it is the OAuth
  redirect base, the base of portal links, the origin of the CSRF check, and an `https://`
  value turns on `Secure` cookies. Without it, the runtime uses `spec.runtime.url` of
  `cicord.yaml`, then (for a configuration created by the setup wizard) the URL the wizard ran
  on, then the listener's own address: `http://localhost:7420` for the default `:7420` (any
  address that is not a wildcard is used as is, for example `http://127.0.0.1:7420`). It logs
  a warning when it falls back. Unsafe requests (`POST`, `PUT`, `PATCH`, `DELETE`) sent with
  an `Origin` that is neither this URL, the admin URL nor an allowed CORS origin are rejected
  with `403`.
- **`--admin-url`** (env `CICORD_ADMIN_URL`): the URL of the admin console when it lives on a
  separate, private hostname, for example `https://cicord.example.ts.net` on a Tailscale
  tailnet, while the portal stays public on `--public-url`. It must be `https://host[:port]`
  without a path (`http` only for a loopback host) and differ from the public URL. Requests
  on that hostname log in with the admin URL, and the admin console and admin API answer
  `404` on every other hostname. See
  [Admin on a private network, portal public](../security/#admin-on-a-private-network-portal-public).
- **`--cors-origin`** (repeatable; env `CICORD_CORS_ORIGINS`, comma-separated): origins of
  external portals allowed to call the API **with credentials** (cookie sessions).
- **`--data-dir`** defaults to `.cicord-data`, relative to the working directory. With a local
  source inside the repository, it must be under `<repo>/.cicord/`.
- **`--database-url`** (env `CICORD_DATABASE_URL`): PostgreSQL connection URL of the
  [state store](#state-store-sqlite-or-postgresql). Unset: SQLite in the data directory, which
  is needed either way. The URL is never logged.
- **`--metrics-listen`** (env `CICORD_METRICS_LISTEN`): address of a separate, unauthenticated
  Prometheus listener, for example `127.0.0.1:9420`. Off by default. See [Monitoring](../monitoring/).
- **`--log-level`**: `debug`, `info` (default), `warn` or `error`.
- **`--github-app-key-file`** (env `CICORD_GITHUB_APP_PRIVATE_KEY_FILE`): the GitHub App
  private key as a file (a Docker or Kubernetes secret mounted as a file), instead of the
  `CICORD_GITHUB_APP_PRIVATE_KEY` secret. See [GitHub access](#github-access-token-or-github-app).

Started in a directory without `cicord.yaml`, `cicord serve` enters [setup mode](../../getting-started/setup-wizard/)
and prints a one-time link to the setup wizard. Once the wizard has activated a
configuration, the same command in the same directory boots from the repository the wizard
created (embedded or GitHub), recorded in the data directory. A data directory that already
belongs to a deployment (it has a sync history or a `repo.git`, but no setup state) is
**refused** rather than set up again: run `cicord serve` in that deployment's repository, or
pass another `--data-dir`.

## Environment variables

| Variable                                   | Purpose                                                                                                                                                                                 |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DISCORD_TOKEN_*`                          | Bot tokens. The name is each bot's `spec.token.secretRef`, e.g. `DISCORD_TOKEN_MODERATOR`. A missing token leaves that bot `Missing`.                                                   |
| `CICORD_GIT_TOKEN`                         | HTTPS token to fetch a private repository, push write-back commits, open GitHub pull requests and set commit statuses (see [GitHub access](#github-access-token-or-github-app)).        |
| `CICORD_GITHUB_APP_ID`                     | GitHub App ID: authenticate as a GitHub App instead of a token (it takes precedence over `CICORD_GIT_TOKEN`).                                                                           |
| `CICORD_GITHUB_APP_PRIVATE_KEY`            | The App's private key (the `.pem` content), or `--github-app-key-file`.                                                                                                                 |
| `CICORD_GITHUB_APP_INSTALLATION_ID`        | The App's installation. Optional: discovered from `spec.source.repo` on github.com.                                                                                                     |
| `CICORD_RUNTIME_TOKEN`                     | Bearer token of the CLI and CI (`cicord plan --remote`, `cicord status`, `cicord sync`, `POST /api/v1/sync`). Acts as admin on every server. Unset: the machine endpoints answer `401`. |
| `CICORD_WEBHOOK_SECRET`                    | Secret of the GitHub webhook (`POST /hooks/github`). Unset: webhooks are rejected.                                                                                                      |
| `CICORD_DISCORD_CLIENT_SECRET`             | OAuth2 client secret for "Log in with Discord" (admin console, portal). Unset: `/auth/login` answers `503`.                                                                             |
| `CICORD_DISCORD_CLIENT_ID`                 | OAuth2 client ID. Default: the application ID of the first bot (by key).                                                                                                                |
| `CICORD_LINK_SECRET`                       | Signing key of portal links. Default: generated once in the data directory (`link.key`).                                                                                                |
| `CICORD_SECRET_KEY`                        | Key of the encrypted secret store: base64 or hex of exactly 32 bytes (`openssl rand -base64 32`). Default: `secret.key`, generated in the data directory.                               |
| `CICORD_PUBLIC_URL`, `CICORD_CORS_ORIGINS` | Defaults of `--public-url` and `--cors-origin`.                                                                                                                                         |
| `CICORD_ADMIN_URL`                         | Default of `--admin-url`: the admin console on a separate, private hostname.                                                                                                            |
| `CICORD_METRICS_LISTEN`                    | Default of `--metrics-listen`: address of the Prometheus metrics listener (see [Monitoring](../monitoring/)). Unset: no metrics.                                                        |
| `CICORD_DATABASE_URL`                      | Default of `--database-url` (also read by `cicord dev` and `cicord secret`): use PostgreSQL for the state store. Unset: SQLite in the data directory.                                   |
| `CICORD_CACHE_DIR`                         | Plugin download cache (`<dir>/plugins`). Default: the user cache directory; the Docker image sets `/data/cache`.                                                                        |
| `CICORD_ALLOW_PRIVATE_REGISTRIES`          | `true` lets the Store and plugin downloads reach registries on private networks. Default: public addresses only.                                                                        |
| `CICORD_REGISTRY_<NAME>_TOKEN`             | Access token of a private registry (see [Publishing](../../plugins/publishing/#private-registries)).                                                                                    |

Bot tokens, `CICORD_GIT_TOKEN`, the `CICORD_GITHUB_APP_*` secrets, the OAuth client secret,
`CICORD_WEBHOOK_SECRET`, `CICORD_RUNTIME_TOKEN` and registry tokens can also live in the
encrypted secret store (the setup wizard writes them there, `cicord secret set` too). The
environment always wins. The webhook secret and the runtime token are read at startup:
restart the runtime after changing them. See [Backups and secrets](../backups-and-secrets/).

In the Discord developer portal, add `<public-url>/auth/callback` as an OAuth2 redirect URL of
the application used for login, and also `<admin-url>/auth/callback` when `--admin-url` is set.

## Data directory

| Path                                             | Content                                                                                                                         | Back up?           |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| `cicord.db` (+ `cicord.db-wal`, `cicord.db-shm`) | SQLite (WAL mode): resource map, plugin storage, sessions, audit log, sync history, encrypted secrets. Absent with PostgreSQL.  | **Yes**            |
| `secret.key`                                     | Key of the secret store (when `CICORD_SECRET_KEY` is not set). Keep one copy **apart** from the routine backups.                | **Yes, apart**     |
| `link.key`                                       | Portal link signing key (when `CICORD_LINK_SECRET` is not set). Regenerated when missing: only links already sent stop working. | No                 |
| `repo.git`                                       | Bare repository of the `embedded` provider: this **is** your configuration.                                                     | **Yes**            |
| `source/`                                        | Clone of the git source.                                                                                                        | No (fetched again) |
| `writeback/`                                     | Work tree used to commit and push admin console edits.                                                                          | No                 |
| `snapshots/`                                     | Snapshots of a local source.                                                                                                    | No                 |
| `cache/` (Docker image)                          | Downloaded plugins.                                                                                                             | No                 |

The resource map in the state store links YAML keys to Discord IDs. Without it, the next sync
adopts the existing resources [by name](../../concepts/reconciliation/#adoption-by-name) again,
so losing it is recoverable but noisy.

Run **a single runtime per data directory, per state database and per set of bot tokens**:
scheduled tasks are not claimed across processes, so two runtimes on one database would run
them twice. Backups are covered in [Backups and secrets](../backups-and-secrets/).

## State store: SQLite or PostgreSQL

The state store holds the resource map, plugin storage, scheduled tasks, sessions, the audit
log, the sync history and the encrypted secrets.

- **SQLite** (default): `cicord.db` in the data directory. Nothing to install or operate.
- **PostgreSQL** (14 or later): set `--database-url` or `CICORD_DATABASE_URL`, for example
  `postgres://cicord@db.internal:5432/cicord?sslmode=verify-full`. Useful when the database is
  managed separately (backups, replication, monitoring).

With PostgreSQL:

- **Keep the data directory.** It still holds `secret.key` (unless `CICORD_SECRET_KEY` is set),
  `link.key` (unless `CICORD_LINK_SECRET` is set), `repo.git` for the embedded provider and the
  caches. The secrets in the database are encrypted with that key: a runtime started with a new
  data directory against an existing database refuses to start. Setting `CICORD_SECRET_KEY`
  removes that dependency.
- **Create an empty database owned by the runtime's user.** Cicord creates and migrates its
  tables at startup (in one transaction, under an advisory lock) and refuses a database whose
  schema is newer than the binary.

  ```sql
  CREATE ROLE cicord LOGIN PASSWORD '…';
  CREATE DATABASE cicord OWNER cicord;
  ```

- **Connection options** go in the URL (libpq/pgx syntax): `sslmode` (use `verify-full`
  across a network), `pool_max_conns` (default: the number of CPUs, at least 4),
  `search_path=<schema>` for a dedicated schema (create it first),
  `default_query_exec_mode=exec` behind PgBouncer in transaction mode. The password can come
  from `PGPASSWORD` or `~/.pgpass` instead of the URL. The startup log shows
  `postgres://user@host:port/database`, never the password.
- **Same behavior as SQLite**: both backends pass the same conformance suite (CI runs it on
  PostgreSQL 19). Text fields other than plugin storage keys and values (server keys, resource
  keys, IDs, scopes) must be valid UTF-8 without NUL bytes, which keys from YAML always are.
  Audit and sync entries are ordered by ID, allocated from a sequence: under concurrent writes
  that is allocation order rather than commit order. Times are stored as `BIGINT` Unix
  nanoseconds and JSON payloads as `BYTEA`; inspect them with
  `convert_from(value, 'UTF8')::jsonb`.
- **No conversion tool** between the backends yet: switching starts from an empty state
  (Discord resources are adopted again by name; plugin data, history and stored secrets are
  not carried over).

With Compose, add a `postgres` service and point the runtime at it:

```yaml title="compose.yaml (excerpt)"
services:
  cicord:
    # the service of the Compose example below, plus:
    environment:
      CICORD_DATABASE_URL: postgres://cicord@postgres:5432/cicord?sslmode=disable
      PGPASSWORD: ${CICORD_DB_PASSWORD} # from .env, keeps the password out of the URL
    depends_on:
      postgres: { condition: service_healthy }
  postgres:
    image: postgres:19
    restart: unless-stopped
    environment:
      POSTGRES_USER: cicord
      POSTGRES_PASSWORD: ${CICORD_DB_PASSWORD}
    volumes: [cicord-pg:/var/lib/postgresql]
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "cicord"]
      interval: 5s
volumes:
  cicord-data:
  cicord-pg:
```

## Docker

Each release publishes the multi-arch image `ghcr.io/cicord/cicord:<version>` (linux/amd64,
linux/arm64), with SBOM and build provenance attestations. Pull the release, verify it
([Installation](../../getting-started/installation/#verify-a-download)) and give it the short
name used below:

```sh
docker pull ghcr.io/cicord/cicord:0.1.6
gh attestation verify oci://ghcr.io/cicord/cicord:0.1.6 --repo cicord/cicord
docker tag ghcr.io/cicord/cicord:0.1.6 cicord
```

To build the same image from a checkout instead (the root `Dockerfile` builds the web UIs
with Node 26 and the pnpm of `packageManager`, then `cicord` with `CGO_ENABLED=0`, on
`gcr.io/distroless/static-debian13:nonroot`):

```sh
docker build -t cicord --build-arg VERSION=0.1.6 --build-arg COMMIT=$(git rev-parse --short HEAD) .
```

The image runs `cicord serve /repo --data-dir /data --listen :7420` as user 65532, with a
volume on `/data`, port `7420` and a `HEALTHCHECK`. `/repo` must contain at least
`cicord.yaml`. The image has no shell: the entrypoint is `cicord`, so
`docker run --rm cicord validate /repo` works too.

- A named volume inherits the ownership of `/data` from the image (65532). For a bind mount,
  `chown 65532:65532` the host directory first.
- For a local source (no `spec.source`), mount the whole repository at `/repo`, writable if
  admin console edits should be saved (`:ro` makes write-back fail).
- **Health**: `GET /healthz` (process up, also in setup mode) and `GET /readyz` (a revision
  is active; `503` before). The image's `HEALTHCHECK` runs
  [`cicord healthcheck`](../../reference/cli/#cicord-healthcheck), which probes
  `http://127.0.0.1:7420/healthz` (every 30 s, timeout 5 s, 3 retries). With another
  `--listen` port, override it with `cicord healthcheck --url http://127.0.0.1:<port>/healthz`.
- Stop with `SIGTERM`: the HTTP server, the bots and the background jobs shut down
  gracefully, which can take up to about 35 seconds (10 s for HTTP, 15 s for the runtime,
  10 s for background jobs). `docker stop` kills the container after 10 seconds by default:
  use `docker stop -t 40` (Compose: `stop_grace_period: 40s`, as in `deploy/vps/compose.yaml`).

## Reverse proxy and TLS

Run Cicord behind a TLS-terminating proxy (Caddy, nginx, Traefik) and keep port 7420 private
(bound to `127.0.0.1` or an internal network).

- `--public-url` must be exactly the scheme, host and port browsers see. The CSRF check compares
  the browser's `Origin` with it, so the proxy must pass `Origin` through unchanged. Without
  `--admin-url`, `Host` is not used by `cicord serve`; with it, `Host` tells the admin
  hostname from the others, so every proxy must pass the original `Host` (Caddy does by
  default, nginx with `proxy_set_header Host $host`).
- Request bodies: JSON up to 1 MiB, `POST /api/v1/plan` up to 32 MiB (for nginx,
  `client_max_body_size 32m`). API handlers time out after 60 seconds and a configuration edit
  may wait up to 20 seconds for the new revision, so keep proxy read timeouts above 60 seconds.
- An external portal on another origin is allowed with `--cors-origin https://portal.example.org`;
  the OAuth `redirect` may then point to that origin.
- `GET /api/v1/events` is a server-sent events stream (live refresh of the admin console): a
  ping every 25 seconds, closed after 10 minutes. The proxy must not buffer it (the runtime
  sends `X-Accel-Buffering: no`, which nginx honors; Caddy flushes event streams) and its read
  timeout must be above 25 seconds.

  location / {
    proxy_pass http://127.0.0.1:7420;
    proxy_set_header Host $host;
    proxy_read_timeout 90s;
  }
}

## GitHub access: token or GitHub App

Every access to the configuration repository (fetch, write-back pushes, pull requests,
commit statuses) uses one of these credentials, resolved like every runtime secret
(environment first, then the encrypted secret store):

- **A personal access token**, `CICORD_GIT_TOKEN`: a fine-grained token restricted to the
  configuration repository, with the permissions below. Simple, but tied to a person and
  long-lived.
- **A GitHub App**, recommended for organizations: commits, pull requests and statuses appear
  as `<app-name>[bot]`. The runtime only holds the App's private key; it mints installation
  tokens that expire after an hour, restricted to the configuration repository, and renews
  them 5 minutes before they expire. When the App is configured, it takes precedence over
  `CICORD_GIT_TOKEN`. The App can only be used with a repository on github.com
  (`https://github.com/owner/name`): its tokens are never sent to another host. For a
  repository hosted elsewhere, use a token.

Repository permissions, the same for a fine-grained token and for the App:

| Permission      | Access         | Used for                                                    |
| --------------- | -------------- | ----------------------------------------------------------- |
| Contents        | Read and write | fetching, write-back commits and `cicord/change-…` branches |
| Pull requests   | Read and write | the `pullRequest` write-back mode                           |
| Commit statuses | Read and write | the [`cicord/sync` commit status](#commit-statuses)         |
| Metadata        | Read-only      | mandatory (selected automatically)                          |

No organization or account permission is needed.

### Create the GitHub App

1. On GitHub, open **Settings → Developer settings → GitHub Apps → New GitHub App** (for an
   organization: the organization's **Settings → Developer settings → GitHub Apps**).
2. Enter a name (it becomes the commit author, for example `acme-cicord[bot]`) and a homepage
   URL (your public URL).
3. **Webhook** is optional. Uncheck _Active_ to rely on polling, or set the webhook URL to
   `<public-url>/hooks/github`, its secret to `CICORD_WEBHOOK_SECRET`, and subscribe to the
   **Push** event (other events are acknowledged and ignored). See [Webhooks](#webhooks).
4. Set the repository permissions of the table above.
5. Under _Where can this GitHub App be installed?_, choose **Only on this account**, then
   create the App.
6. Note the **App ID** (General → About). Under **Private keys**, click **Generate a private
   key**: GitHub downloads a `.pem` file.
7. Open **Install App**, install it on the account that owns the configuration repository,
   choose **Only select repositories** and pick the configuration repository.

### Give the runtime the App

| Secret                              | Value                                                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `CICORD_GITHUB_APP_ID`              | The App ID (the client ID works too).                                                                                                            |
| `CICORD_GITHUB_APP_PRIVATE_KEY`     | The content of the `.pem` file (RSA, PKCS#1 or PKCS#8). A single line with literal `\n` is accepted (env files); or use `--github-app-key-file`. |
| `CICORD_GITHUB_APP_INSTALLATION_ID` | Optional on github.com (discovered from the repository): the number at the end of the installation's settings URL.                               |

Set them as environment variables, or store them encrypted:

```bash
cicord secret set CICORD_GITHUB_APP_ID --data-dir /data   # type the App ID, then Enter
cicord secret set CICORD_GITHUB_APP_PRIVATE_KEY --data-dir /data < acme-cicord.private-key.pem
```

In the [setup wizard](../../getting-started/quick-start/), the Repository step offers
**GitHub App** next to the token: it checks the App by getting a token and reading the
repository, then stores these secrets. A partial configuration (an App ID without a key, or
the reverse) stops `cicord serve` with an error naming what is missing. The startup log says
which method is used, never the secret. GitHub Enterprise Server is not supported yet.

## Commit statuses

With `provider: github` and credentials, every commit the runtime evaluates gets a commit
status with the context **`cicord/sync`**:

- `pending` while the revision is validated and applied;
- `success` once it is applied to every server, every bot is connected and every plugin
  instance started;
- `failure` when it is rejected (validation or plugin build), a server failed (no connected
  bot, the bot cannot access the server, or the sync failed), a server is
  [paused](../../concepts/reconciliation/#emergency-pause-enforcement) (the revision is not
  applied to it), a bot is not connected, or a plugin instance failed to start. The
  description names the first problem and counts the others, for example
  `2 problems; Server my-community paused by owner: not applied`. Changes that only wait for
  a boost level do not fail it. Once the problems are gone (the server resumed and synced, for example), the
  status of the active commit turns `success`; a problem that appears later is runtime
  health ([alerts](../monitoring/#alerts), `cicord status`), not a new failure.

The status links to `<admin-url>/admin/` when `--admin-url` is set, otherwise to
`<public-url>/admin/`, unless that URL is a loopback address. When the credentials lack the
_Commit statuses_ permission, the runtime logs a warning (`GitHub commit status not set`,
once; then at debug level) and the sync goes on. Statuses are set on the commits of the
tracked branch, after the merge; to check a pull request before merging, run
`cicord plan --remote --comment` in CI, which comments the plan on the pull request
([Your first change](../../getting-started/first-change/#run-it-in-ci)).

## Webhooks

The runtime polls its git source (every minute by default). For instant syncs, add a GitHub
webhook:

| Setting      | Value                                                                           |
| ------------ | ------------------------------------------------------------------------------- |
| Payload URL  | `<public-url>/hooks/github`                                                     |
| Content type | `application/json`                                                              |
| Secret       | the value of `CICORD_WEBHOOK_SECRET` (signatures are verified with HMAC-SHA256) |
| Events       | `push`                                                                          |

Pushes to the tracked branch trigger a sync; polling still runs as a fallback. Without a
webhook, `cicord sync` (with `CICORD_RUNTIME_TOKEN`) asks the runtime to fetch now.
